# Design tokens via per-project config: does any TanStack library help?

**Date:** 2026-09-02
**Sources:** primary only — tanstack.com docs (scraped live on this date) and the repo itself. Firecrawl scrapes archived under `.firecrawl/`.

## TL;DR

**Verdict: no.** No TanStack library offers config-file-driven design tokens or a theming system for application chrome. The name `@tanstack/config` is a false friend — it is library _publishing_ tooling (dual ESM/CJS builds, ESLint, publish config, package-structure conventions), not runtime or app configuration ([Config docs](https://tanstack.com/config/latest/docs/vite)). TanStack Start's build config is the `tanstackStart()` Vite/Rsbuild plugin, which governs build/SSR concerns; its CSS guidance is about stylesheet _delivery_ (side-effect imports, CSS modules, inlining), not tokens ([CSS Styling guide](https://tanstack.com/start/latest/docs/framework/react/guide/css-styling)). The single closest thing in the ecosystem is `@tanstack/highlight/theme`, which "converts portable theme objects into CSS custom properties" — but for syntax-highlighting token classes only ([Highlight Theme API](https://tanstack.com/highlight/latest/docs/reference/theme)).

**Recommended course:** keep what the repo already has. The existing pipeline (`workbench.config.json` → `scripts/config.mjs` normalization with alias mapping → baked into `src/data.generated.ts` → CSS custom properties applied in `src/main.tsx` → consumed as `var(--…)` in `src/styles.css`) is exactly the pattern the TanStack ecosystem itself leaves to the app. Nothing to adopt; optionally use TanStack Store later _only if_ themes must switch at runtime.

## 1. What the repo does today (the baseline)

- `workbench.config.json` is read by `loadWorkbenchConfig()` in `scripts/config.mjs` (line 138). The `theme` object uses friendly token names (`text`, `background`, `accent`, …) constrained to hex colors by `workbench.config.schema.json`.
- `normalizeTheme()` (line 72) validates each value and maps friendly names onto the 17 runtime token names via `themeAliases` (`text → ink`, `background → bg`, `accent → acid`, …), merged over the frozen `DEFAULT_THEME` (line 4). Missing keys silently fall back to defaults.
- `scripts/sync-data.mjs` (line 488) bakes the normalized theme into the generated bundle: `theme: config.theme` lands in `overviewData.meta.theme` inside `src/data.generated.ts` ("Generated by `pnpm workbench sync`. Do not edit by hand.").
- `src/main.tsx` (lines 9–14) applies the tokens at startup: `document.documentElement.style.setProperty(`--${name}`, value)` for each entry, plus `meta[name="theme-color"]` and `document.title`.
- `src/styles.css` consumes them as `var(--ink)`, `var(--bg)`, `var(--acid)`, including `color-mix(in srgb, …)` derivations.
- The runtime token shape is `WorkbenchTheme` in `src/types.ts` (lines 81–99).

This is a build-time whitelabel pipeline: config is consumed by Node scripts, frozen into generated data, and hydrates as CSS custom properties before React mounts.

## 2. Candidate-by-candidate: what each TanStack library actually offers

### `@tanstack/config` — NOT design tokens (repo/publish tooling)

The docs confirm this is internal tooling for publishing TanStack's own libraries: the Vite page exists because "The Vite build setup was the result of several attempts to dual publish ESM and CJS for TanStack projects, while preserving compatibility with all Typescript module resolution options," and the docs sidebar covers ESLint, Publish, CI/CD, and Package Structure ([Config / Vite](https://tanstack.com/config/latest/docs/vite)). It is explicitly not general-purpose: "The build config is opinionated, and was designed to work with our internal libraries," and it is being wound down — "We will be adopting tsdown for future projects rather than continuing to use our custom Vite setup" ([Config / Vite](https://tanstack.com/config/latest/docs/vite)). Nothing here touches app themes or design tokens.

### TanStack Start — plugin config is build/SSR concerns; CSS docs cover delivery, not tokens

Start's project configuration is the `tanstackStart()` plugin inside `vite.config.ts` (`import { tanstackStart } from '@tanstack/react-start/plugin/vite'`), or the Rsbuild equivalent (`@tanstack/react-start/plugin/rsbuild`) ([Build from Scratch](https://tanstack.com/start/latest/docs/framework/react/build-from-scratch)). Its options concern the build pipeline and server (e.g. `server.build.inlineCss`), not design systems. The dedicated [CSS Styling guide](https://tanstack.com/start/latest/docs/framework/react/guide/css-styling) is entirely about stylesheet _discovery and delivery_: `?url` imports in route `head()`, side-effect global imports, CSS Modules, when CSS is discovered, and inlining route CSS in production via `server.build.inlineCss`. It prescribes no token format, no theme object, and no dark-mode mechanism; the current React docs sidebar contains no theming page at all (captured scrape: `.firecrawl/start-css-styling.md`). A Tailwind integration guide exists ([Tailwind CSS Integration](https://tanstack.com/start/latest/docs/framework/react/guide/tailwind-integration)), but that is third-party styling-tool integration, not a TanStack token system.

**What Start does offer workbench-relevant:** nothing needed now. If workbench ever migrated to Start, the existing `styles.css` + `var(--…)` approach carries over unchanged — Start's CSS handling treats global stylesheets and CSS Modules as first-class ([CSS Styling guide](https://tanstack.com/start/latest/docs/framework/react/guide/css-styling)).

### TanStack Store — could _hold_ theme state, but has no config-file or token features

Store is "a framework-agnostic signals implementation with immutable updates, derived values, batching, and adapters that let components select only the state they render," positioned as a reactive primitive that "provides the reactive primitive without prescribing a product-wide state architecture," with the guidance: "Reach for Store when state is local to the client and benefits from reactive derivation" ([Store](https://tanstack.com/store/latest)). Nothing in it reads config files or generates CSS. It is a plausible home for _runtime_ theme switching (user picks a theme in-session, components react), which workbench does not currently need — the theme is fixed per generated snapshot.

### TanStack Highlight — the one real "theme object → CSS variables" API, but scoped to code blocks

`@tanstack/highlight/theme` "converts portable theme objects into CSS custom properties and base styles. It contains no bundled theme," exposing `themeTokenClasses`, `HighlightTheme`/`HighlightThemeToken`, `createThemeCss`, `createThemeRule`, and `createThemeBaseCss` ([Highlight Theme API](https://tanstack.com/highlight/latest/docs/reference/theme)). This is architecturally the closest analogue to workbench's pipeline (portable theme object → CSS custom properties), but its token classes are syntax-highlighting scopes for code blocks, not app-level surface/accent/border tokens. Not applicable to whitelabeling the whole app.

### TanStack Table — headless, deliberately opinionated about styling

Table describes itself as "Headless, type-safe table and data-grid infrastructure" ([tanstack.com/table](https://tanstack.com/table/latest)); its docs contain no styling/theming guide — the closest is [Column Sizing](https://tanstack.com/table/latest/docs/framework/react/guide/column-sizing), which uses inline `style` widths (a search of tanstack.com for a table styling guide surfaces no dedicated page; scrape archive: `.firecrawl/search-table-styles.json`). Workbench already does the right thing here: `src/lib/table.ts` wires features headlessly and `src/styles.css` owns all visuals via `var(--…)` tokens, so config-driven themes reach the tables with zero Table-specific work.

### The rest (Query, Router, DB, AI, Form, Charts, Hotkeys, Markdown, Virtual, Pacer, Ranger)

None of these concern design tokens: they are data fetching/caching, routing/server functions, local-first DB, AI transport, form state, charting, keymaps, markdown rendering, window virtualization, and utility-rate/scheduling/range libraries respectively — none markets theming or token configuration (the [tanstack.com library landscape](https://tanstack.com/libraries) captured in every scrape shows the categories; the site-wide search for "design tokens CSS variables theming" surfaced only Highlight's Theme API and Start's CSS guides — `.firecrawl/search-tokens.json`). The repo's existing TanStack Router/Table usage is unaffected either way.

## 3. Recommended approach for workbench

Keep the current pipeline — it already implements the pattern the TanStack ecosystem expects apps to own (tokens as CSS custom properties on `:root`, consumed by headless component styling):

1. **No library adoption.** There is no TanStack API to swap in; `@tanstack/config` is publishing tooling, Start's config is a build plugin, and Highlight's theme API is code-highlighting-specific (all cited above).
2. **If hardening is wanted, it is app-local:** `normalizeTheme()` in `scripts/config.mjs` hand-rolls validation (hex pattern, alias mapping) that could be expressed once as a JSON-Schema-derived check, and unknown extra keys in `theme` are currently ignored rather than rejected (the schema says `additionalProperties: false` but the script-side normalizer doesn't enforce it).
3. **If runtime theme switching is ever needed** (e.g. light/dark per user, overriding the project bake), TanStack Store is the ecosystem-consistent primitive for holding the active theme as reactive state and deriving side effects — but per its docs it is for client-local reactive state, not config-file loading ([Store](https://tanstack.com/store/latest)). Until then, the one-shot `setProperty` loop in `src/main.tsx` is simpler and sufficient.
4. **If the app ever moves to TanStack Start**, nothing changes for theming: keep `styles.css` with `var(--…)` and (optionally) let Start's `server.build.inlineCss` reduce first-load CSS blocking ([CSS Styling guide](https://tanstack.com/start/latest/docs/framework/react/guide/css-styling)).
