## TL;DR

**Verdict: yes — and the theming groundwork is already done.** The goal is visual/layout only: give workbench the shadcn-ui-kit-dashboard shell anatomy (collapsible `Sidebar` + sticky `SiteHeader` + `SidebarInset` content frame + dashboard-style tokens) without touching routes, loaders, URL search state, filtering, or table behavior. The expensive part of that migration — shadcn semantic tokens driven by the config theme — already exists (`src/styles.css:12-35` maps `--background/--primary/--border/…` onto the legacy `--bg/--acid/--line/…` vars that `src/main.tsx:9-10` injects from `workbench.config.json`). What is missing is structural: workbench has **no sidebar, no shared layout component, and no nav model** — each page hand-renders its own sticky header (`OverviewPage.tsx:100-143`, `SessionsPage.tsx:79-104`), and navigation between the two routes is a pair of plain `<a href>` links. The reference repo's shell is the stock shadcn `sidebar.tsx` primitive (703 lines, `components/ui/sidebar.tsx`) plus ~250 lines of app glue (`app-sidebar.tsx`, `nav-main.tsx`, `header/index.tsx`), so the plan is: vendor the sidebar primitive + its four missing UI deps, add a `--sidebar-*` token layer defined in terms of the existing legacy vars (config stays authoritative), and rebuild the glue on TanStack Router instead of Next's `usePathname`/`Link`. Next-specific machinery (next-themes, cookies-in-server-layout, next/font, the cookie-driven theme customizer) is translated or deliberately not copied.

Estimated effort: **2–3 dev-days**, gated by the same single smoke test as the 2026-09 shadcn adoption (`pnpm dev` / `build` / `test` / `check` — the Tailwind-under-vite-plus risk from `docs/research/shadcn-adoption.md` §3/§10 is already retired, since that migration shipped).

## 1. Question

Can workbench's app shell — sidebar/navigation, header, page scaffolding, and theming — be made to look and lay out like the reference repo `shadcn-ui-kit-dashboard` **with zero functionality changes**? Routes (`/` and `/sessions`), their `validateSearch`/`stripSearchParams` contracts, loaders, filtering logic, and table behavior must remain byte-for-byte identical; only the visual chrome and the component/layout structure that surrounds page content may change. This note inventories both shells from source, diffs them, and proposes an ordered plan.

## 2. Current state (workbench)

**Routing/shell ownership.** TanStack Router file-based routing with a deliberately empty root: `src/routes/__root.tsx:3-5` is just `component: () => <Outlet />` — **no shell, no providers, no layout**. Two leaf routes mount page components that each own their full chrome:

- `src/routes/index.tsx:28-35` — route definition (`validateSearch` zod schema, `stripSearchParams` middleware, `loader: () => overviewData`), renders `OverviewPage` with search + `updateSearch` callbacks (`index.tsx:37-59`).
- `src/routes/sessions.tsx:13-20` — same shape for `/sessions` → `SessionsPage`.
- Router instance: `src/router.tsx:5-9` (`defaultPreload: "intent"`, `scrollRestoration: true`). Plugins in `vite.config.ts:17-22` (`tanstackRouter`, `react`, `tailwindcss`, `@` alias).

**Shell anatomy per page (duplicated twice).** `OverviewPage.tsx:100-143` and `SessionsPage.tsx:79-104` both render:

1. `<main className="app-shell">` — centered column, `width: min(100% - 56px, 1540px)` (`styles.css:204-209`);
2. two decorative `.ambient` blur blobs (`OverviewPage.tsx:102-103`; `styles.css:211-232`);
3. a sticky `.site-header` (`styles.css:234-242`: `position: sticky; backdrop-filter: blur(14px)`) containing a `.topline` eyebrow row, a `.brand-row` with the "work**bench**" wordmark, and `.header-actions` — the read-only badge, a raw `<a href="/sessions">` cross-link (`OverviewPage.tsx:122`) and its reciprocal `<a href="/">` (`SessionsPage.tsx:101`), plus the repository link;
4. Overview only: a sticky in-page `.section-nav` with `#tickets`/`#plans`/`#specs`/`#sources` anchors (`OverviewPage.tsx:132-143`; `styles.css:379-390`).

Everything below the header is page content (metric grid, callouts, filter card, tables, footer — `OverviewPage.tsx:145-316`). There is **no navigation component, no sidebar, no hooks directory, no shared layout** — the only cross-page nav is those two anchor tags.

**Styling system.** One hand-authored CSS file, `src/styles.css` (922 lines), compiled by Tailwind v4 via `@tailwindcss/vite` (`vite.config.ts:17`). The shadcn semantic layer was added by the earlier migration and sits in `@theme inline` (`styles.css:12-35`): `--color-background: var(--bg)`, `--color-primary: var(--acid)`, `--color-border: var(--line)`, radius scale off `--radius`, etc. The legacy tokens themselves live in `:root` (`styles.css:79-104`) — **dark-only** (`color-scheme: dark`, `styles.css:81`; `@custom-variant dark` declared at `styles.css:4` but no `.dark` block exists), `--radius: 0rem` (deliberately sharp, `styles.css:80`), sans stack `"Avenir Next", "Segoe UI"` (`styles.css:100`), mono stack (`styles.css:69,183-185`), serif display for section headings (`styles.css:367`). Body carries a radial-gradient wash + grid overlay (`styles.css:114-142`).

**Config theme flow (the invariant).** `workbench.config.json` → `theme` block with friendly names (`workbench.config.example.json:7-16`) → `normalizeTheme()` in `scripts/config.mjs:90-101` maps them through `themeAliases` (`config.mjs:24-41`) onto the 17 runtime names of `DEFAULT_THEME` (`config.mjs:4-22`) → baked into `src/data.generated.ts` by `pnpm sync` → applied before React mounts in `src/main.tsx:9-10` as `documentElement.style.setProperty("--${name}", value)` — i.e. **inline-style custom properties on `<html>`**, which beat the `:root` defaults and therefore re-tint the whole `@theme inline` layer. `WorkbenchTheme` type: `src/types.ts:86-104`. Any re-skin must keep every new token defined _in terms of the legacy names_ or config themes silently stop working for it.

**shadcn inventory.** Nine vendored primitives in `src/components/ui/`: `badge`, `button`, `card`, `input`, `native-select`, `progress`, `table`, `toggle`, `toggle-group`. `components.json:1-19` (`style: new-york`, Tailwind v4 with blank config, `css: src/styles.css`, `@` aliases wired). Runtime deps already present: `radix-ui` unified (`package.json:45`), `class-variance-authority`, `clsx`, `tailwind-merge`, `tw-animate-css` (`package.json:42-50`). **`lucide-react` is not installed anywhere** (grep over `package.json` + `src` returns nothing), and there is no `sheet`/`tooltip`/`separator`/`skeleton`/`dropdown-menu`/`collapsible`/`scroll-area`/`avatar`/`command` component.

## 3. Target state (shadcn-ui-kit-dashboard)

**Framework.** Next.js 16.3.2 App Router + React 19, Tailwind v4 via `@tailwindcss/postcss`, shadcn "radix-nova" style (`package.json:59,86`; `components.json`). Notably it also runs `next-themes`, `lucide-react`, `cmdk`, and the unified `radix-ui` package (`package.json:50,56,60,62`) — the same primitive family workbench already vendors. Its README self-describes as "Next.js, React 19, and shadcn/ui … Tailwind CSS v4" (README, Tech Stack table).

**Shell anatomy — three composed layers:**

1. **Root layout** (`app/layout.tsx`): `ThemeProvider attribute="class" defaultTheme="light" enableSystem` from next-themes (`layout.tsx:59-63`); `ActiveThemeProvider` writes per-user `data-theme-*` attributes + cookies from a theme-customizer UI (`layout.tsx:26-48,55-58`; `components/active-theme.tsx:23-125`); DM_Sans loaded as `--font-sans` via `next/font` (`layout.tsx:18`); a global `TooltipProvider` and Toaster wrap the app (`layout.tsx:65-67`).
2. **Dashboard layout** (`app/dashboard/(auth)/layout.tsx`): the actual shell. `SidebarProvider` sets layout metrics as inline CSS vars — `--sidebar-width: calc(var(--spacing) * 64)` (16rem), `--header-height: calc(var(--spacing) * 14)`, `--content-padding`, `--content-margin`, `--content-full-height` (`(auth)/layout.tsx:19-30`) — then `AppSidebar` + `SidebarInset > SiteHeader + content` (`:31-39`). Content scaffolding is a `@container/main` div with `p-(--content-padding)` and an opt-in centered variant (`max-w-7xl mx-auto`) driven by `data-theme-content-layout` (`:35`).
3. **Sidebar primitive** (`components/ui/sidebar.tsx`, 703 lines): the stock shadcn sidebar, unmodified in its core. `SidebarProvider` context (open/openMobile/isMobile/toggleSidebar, `:34-53`) renders the `group/sidebar-wrapper min-h-svh` frame (`:140`); `Sidebar` accepts `variant: "sidebar" | "floating" | "inset"` and `collapsible: "offcanvas" | "icon" | "none"` (`:161-162`), renders mobile as a `Sheet` (`:181-206`), stamps `data-variant`/`data-collapsible` (`:212-214`), and implements the icon-rail width math (`:224-237`). Also `SidebarTrigger` (`:254-278`), `SidebarRail` (`:280-303`), `SidebarInset` — the `<main>` that gets inset margins/rounding under `variant=inset` (`:305-316`) — and `SidebarInput` (`:318-330`). State persists to a client-side cookie (`:27-32,85`).

**Sidebar app glue** (`components/layout/sidebar/`):

- `app-sidebar.tsx:29-95` — `Sidebar` with variant/collapsible taken from theme config (`:50-53`; defaults `inset` + `icon`, `lib/themes.ts:1-12`), `SidebarHeader` with logo + product name (`:54-68`), the ⌘K `Search` (`:67`), `SidebarContent > ScrollArea > NavMain` (`:69-73`), `SidebarFooter` promo card (`:74-92`). Auto-collapses on tablet via `useIsTablet` (`:39-47`, hook at `hooks/use-mobile.ts:17-31`, breakpoints 768/992).
- `nav-main.tsx` — `navItems: NavGroup[]` data (grouped, icon per item, `isNew`/`isDataBadge` badges, nested sub-items, `:71-402`); `NavMain` renders groups with `SidebarGroupLabel`, `Collapsible` sub-menus (`:443-469`), a `DropdownMenu` fallback for icon-rail mode (`:419-442`), and `SidebarMenuButton isActive tooltip asChild > Link` for leaves (`:472-480`). Active state comes from `usePathname()` (next/navigation, `:62`).
- `search.tsx:30-110` — read-only `SidebarInput` + `⌘K` kbd that opens a `CommandDialog` (cmdk) listing `navItems`.

**Header** (`components/layout/header/index.tsx:15-45`): one sticky bar inside `SidebarInset` — `bg-background/40 backdrop-blur-md border-b h-(--header-height)` (`:19`) — with the sidebar toggle (`PanelLeftClose/Open`, `:21-23`) and a `StoreSwitcher` workspace dropdown on the left (`:24`; `store-switcher.tsx:38-60`), and on the right a Notifications popover, a light/dark `ThemeSwitch` (`theme-switch.tsx:21-30`), the theme-customizer panel, a vertical `Separator`, and a `UserMenu` avatar dropdown (`user-menu.tsx:111-193`, includes a dark-mode `Switch` item at `:172-183`). **There are no breadcrumbs** (grep over `components/layout/` returns none) — the header is toggle + switcher + action cluster.

**Theming.** `app/globals.css` is Tailwind v4 CSS-first: `@custom-variant dark` (`:3`), imports `./themes.css`, `tw-animate-css`, and `shadcn/tailwind.css` (`:5-7`); `:root` holds oklch tokens **including the full `--sidebar` / `--sidebar-foreground` / `--sidebar-primary` / `--sidebar-accent` / `--sidebar-border` / `--sidebar-ring` set** (`:9-45`); `.dark` overrides the same names (`:47-79`); `@theme inline` exposes them as utilities plus `--font-display`/`--font-sans` and an extended radius scale to `4xl` (`:81-137`, sidebar mapping at `:121-128`). `app/themes.css` (1,261 lines) layers preset palettes as `[data-theme-preset="…"]` blocks with 50–1000 scales feeding the semantic tokens, each with a nested `@variant dark` block (`:8-100`). Fonts are 10 Google families hoisted into `--font-*` vars by `next/font` (`lib/fonts.ts:16-86`), switchable at runtime.

**Cosmetic vs structural in the target.** Cosmetic (pure look): oklch neutral palette + rounded corners (`--radius: 0.625rem` in `:root`, `globals.css:31`), inset sidebar card look, blurred translucent header, `data-theme-*` preset palettes. Structural (layout machinery): the `SidebarProvider → AppSidebar + SidebarInset` frame, the sticky header inside the inset, `--header-height`/`--content-padding` CSS-var scaffolding, and the grouped nav data model.

## 5. Plan

Ordered so that every step leaves the app shippable and the final step deletes the old chrome. Guardrails repeated per step: **never touch** `src/routes/index.tsx` / `sessions.tsx` search schemas, loaders, or the `updateSearch` wiring; `src/lib/overview.ts` filters; `SortableTable`/`TicketTable`/`PlanTable` logic; `scripts/config.mjs`, `workbench.config.schema.json`, `src/types.ts:86-104`; the `src/main.tsx:9-14` injection loop.

1. **Dependencies (0.5 h).** `pnpm add lucide-react`. Files: `package.json` only. Must land in `dependencies` (not dev) because `src` ships in the tarball and compiles on the consumer machine (`shadcn-adoption.md` §8). No other new packages — `radix-ui` unified is already present (`package.json:45`) and covers sheet/dropdown/collapsible/tooltip/scroll-area primitives. cmdk (for the ⌘K search) is deferred to step 8; the plan works without it.
2. **Vendor missing primitives (1 h).** `pnpm dlx shadcn@latest add separator sheet skeleton tooltip scroll-area collapsible dropdown-menu avatar` — CLI writes into `src/components/ui/` per `components.json:12-18`. Must NOT change: existing nine primitives. Add `src/hooks/use-mobile.ts` (copy from the reference `hooks/use-mobile.ts:5-31` — pure React, no Next imports).
3. **Sidebar token layer (1 h).** In `src/styles.css`, add to `:root` and `@theme inline` — defined **only** in terms of existing legacy vars so the config pipeline keeps driving them: `--sidebar: var(--panel)`, `--sidebar-foreground: var(--ink)`, `--sidebar-primary: var(--acid)`, `--sidebar-primary-foreground: var(--bg)`, `--sidebar-accent: var(--panel-hi)`, `--sidebar-accent-foreground: var(--ink)`, `--sidebar-border: var(--line)`, `--sidebar-ring: var(--acid)`, plus `--color-sidebar*` mappings mirroring `globals.css:121-128`. Also add shell layout vars matching the reference's contract: `--header-height`, `--content-padding` (`(auth)/layout.tsx:23-26`). Must NOT change: the existing `--color-*` map (`styles.css:12-35`), `:root` legacy values, `main.tsx`. This step alone is invisible until the shell lands — safe checkpoint.
4. **Shell components (0.5–1 day).** New files under `src/components/layout/`, adapting the reference glue:
   - `app-sidebar.tsx` — `SidebarProvider` (with the sidebar-width/header-height style vars) + `Sidebar variant="inset" collapsible="icon"`; `SidebarHeader` keeps the existing "work**bench**" brand (move `.brand` markup from `OverviewPage.tsx:112-117`); `SidebarContent > NavMain`; `SidebarFooter` absorbs the current `.local-badge` ("read-only / local") and repository link (`OverviewPage.tsx:119-127`).

Collapsible sub-menus and the icon-mode `DropdownMenu` (reference `:419-442,443-469`) can be copied only if/when workbench has nested routes — start with the flat leaf path.
   - `site-header.tsx` — sticky bar per `header/index.tsx:19` classes: `SidebarTrigger` + project name (from `data.meta.projectName`, replacing `StoreSwitcher`) left; right side keeps exactly today's actions (snapshot line from `OverviewPage.tsx:107-109`, sessions/repo links). Theme toggle and user menu omitted in phase 1 (no auth, dark-only) — see Risks.
   - Must NOT change: no data fetching, no routing config in these files beyond link targets that already exist.
5. **Mount the shell in the root route (0.5 h).** `src/routes/__root.tsx:3-5` becomes `SidebarProvider > AppSidebar + SidebarInset > SiteHeader + <Outlet/>` (the direct analogue of `(auth)/layout.tsx:19-39`, minus Next's server cookies). 8. **Optional polish (post-phase-1):** ⌘K command palette (`cmdk`, vendoring `command.tsx`; translate `search.tsx:30-110`'s `router.push` to TanStack `navigate`); light/dark toggle via a ~15-line `useTheme` hook that flips `document.documentElement.classList` + `localStorage` (the explicit next-themes translation the brief requires — only if a light palette is authored, which also means filling the `@custom-variant dark` half of the tokens); `SidebarRail`, nav badges, notification menu.

## 6. Risks / open questions

1. **Radius identity (open question #1).** The reference look is rounded (`--radius: 0.625rem`, rounded-xl inset, `globals.css:31`/`sidebar.tsx:310`); workbench is deliberately sharp (`--radius: 0rem`, `styles.css:80`, called out as intentional in `shadcn-adoption.md` §7). Flipping `--radius` is one line but changes brand feel everywhere at once. Decide before step 4: adopt the reference radius, or keep `0rem` and accept a "sharp dashboard" hybrid.
2. **Dark-only vs the reference's light default (open question #2).** The target's tokens assume a light theme with a `.dark` overlay (`globals.css:47-79`); workbench has only dark values, hoisted into `:root`. Vendored components are token-driven so they render correctly either way, but a phase-1 light mode would need an authored palette — hence dark-only first (Risks item feeds the phase-2 toggle in plan step 8).
3. **Config-theme coverage rule.** `main.tsx:9-10` overrides exactly the 17 legacy names; any future token not derived from them (e.g. a hard-coded oklch chart color) silently ignores user config. The step-3 mapping and the §7 table in `shadcn-adoption.md` are the enforcement pattern — worth a lint/test if the token set grows.
4. **Published-package weight.** `lucide-react` + six vendored primitives grow the tarball the consumer compiles (`package.json:7-15` ships `src`); consistent with the existing model but worth a `pnpm pack` smoke test per `shadcn-adoption.md` §8.
5. **Sticky-header interplay.** Today's `.section-nav` sticks under the page header (`styles.css:379-390`, `top: 95px`); inside the new frame the sticky context changes (header is inside `SidebarInset`, per `header/index.tsx:19`), so scroll-margin/offsets (`styles.css:513-515`) need a visual pass. Pure CSS, but easy to get subtly wrong.
6. **Table chrome inside the inset.** The vendored `Table` deliberately leaves scrolling to `.table-shell` ("Keep the shell as the only scroll context", `styles.css:560-564`). Moving tables into a padded container must not introduce a second scroll owner or sticky header tracking breaks. Check on wide tables after step 7.
7. **vite-plus/Tailwind pipeline** — retired as a risk by the shipped shadcn migration, but the reference's `@container/main` (container query, `(auth)/layout.tsx:35`) is new usage under `vp`; verify the `@container` utility compiles in the step-4 smoke test.
