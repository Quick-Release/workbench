# Software factory adoption model — in-repo, repo-agnostic, or hybrid

Status: research input. On 2026-11-04 the owner accepted all eight suggested answers under "Open questions — suggested answers". They are recorded in ADRs 0024–0026 and in the Factory section of CONTEXT.md.

Work item: none yet (owner question, 2026-11-04). Related: [#158](https://github.com/Quick-Release/workbench/issues/158) (AI software factory map), [#125](https://github.com/Quick-Release/workbench/issues/125) (Host Repo Doctor), [#173](https://github.com/Quick-Release/workbench/issues/173) (parallel runs), [#174](https://github.com/Quick-Release/workbench/issues/174) (remote runners).

## Question

Workbench is meant to be the foundation of the company's **software factory**: one set of base ideas and opinions — workflow, labels, skills, gates, agent runs, review rules — applied to many projects. The owner is not sure the current adoption model is right. Three questions:

1. What does "software factory" mean — in its established senses and in Zach Lloyd's talk [_Software Engineering Is Becoming Factory Engineering_](https://www.youtube.com/watch?v=tUPPVhBBcoM)?
2. Given that, does Workbench's concept need to change?
3. Should Workbench be added to a project **inside the host repository** (today: "A workbench install serves exactly one host repo", [CONTEXT.md](../../CONTEXT.md)), **repo-agnostic** (one central factory pointed at many repos), or a **hybrid** (thin per-repo manifest + shared central opinions/runtime)? What would migration look like?

Labels used throughout: **[fact]** = verified in a cited source or in this repository at `1c71882`; **[inference]** = this note's reasoning; **[proposal]** = a suggested change that needs a decision.

## Summary and recommendation

- **Meaning.** "Software factory" has meant three different things, and the owner's intent combines two of them. Microsoft's 2004 sense is a _product line_: a schema plus a template that configures tools, processes and content for a family of similar products. The DoD sense is a _shared platform plus per-team pipelines_: centrally hardened tooling and inherited authority that many programs build on. The 2025–26 AI sense is an _automated SDLC loop_ with agents at each stage and humans at chosen gates. "One set of opinions applied to many projects" is the first two senses; "agents triage, spec, implement, review" is the third.
- **The talk** (Zach Lloyd, Warp; AI Engineer channel, uploaded 2026-09-27; auto-caption transcript obtained) describes the third sense. Every sizable project gets a factory "like CI/CD"; the floor "looks pretty similar for every product"; the interesting per-project work is _tuning_ — "are these the right skills for my domain?" — plus humans at spec, code-review and product-review gates, and self-improving skill loops. Its architecture is cloud-hosted (control plane, sandboxes, data plane), and Warp's own Warp Factories product keeps one central factory definition that lists the repositories it serves.
- **Workbench today** is already a de-facto hybrid, but only by accident. Its opinions are spread over five homes: package defaults, upstream skills at HEAD, per-repo copied conventions docs, hand-created tracker labels, and Workbench's own repo-only gates. None of them has a name or version, and the gates (protected main, required CI, human merge instruction) do not travel to host repos at all.
- **Recommendation: option C — hybrid, split on the right line [proposal].** Opinions become a central, versioned **Factory baseline**. Each host repo commits a thin **Baseline adoption** (baseline id + version + declared deviations). The runtime stays local and serves exactly one host repo per running instance. Do **not** build a repo-agnostic central factory now: it reverses ADR 0005, needs multi-repo authority in contracts that bind to one canonical repository (ADRs 0020–0022), cannot ship in the public product (ADR 0013), and would move content off the machine (ADR 0001/0013).
- **Drift and upgrades** follow what Copier, cruft, projen, Renovate and the `skills` CLI do. A read-only conformance check (the #125 doctor, with a CI exit code) makes drift visible. Baseline upgrades arrive as reviewed host PRs, never silent edits.
- **Hard gates** go to the platform. GitHub organization rulesets (no per-repo file, most-restrictive-wins) and optionally a SHA-pinned reusable CI workflow enforce them; Workbench describes and observes them, it does not enforce them.
- **Migration** is incremental, and none of it needs a hosted service. Name the baseline inside the existing package, add `baseline` to the config, pin skill installs, ship the doctor, add `workbench upgrade`, publish the ruleset; a multi-repo _read-only_ view and baseline-version Telemetry are optional later steps. A host with no `baseline` field behaves exactly as today.

## What "software factory" means

Sources were read on 2026-11-04. Several DoD/GAO sites refuse automated fetches, so those official URLs were read through Wayback Machine captures of the same URL; this is noted where it applies.

**1. Organizational model (1960s–1990s).** Michael Cusumano's _Japan's Software Factories_ (Oxford University Press, 1991, [publisher page](https://academic.oup.com/book/52424)) describes Japanese firms that "have created what are called 'software factories' in which large numbers of people are engaged in developing software in co-operative ways". Its chapter 4 covers Hitachi; see also Cusumano's 1987 MIT working paper ["Hitachi — pioneering the 'factory' model for large-scale software development"](https://dspace.mit.edu/handle/1721.1/48050) **[fact]**. The commonly cited 1969 date for Hitachi's software works could not be confirmed from a primary text here **[unverified]**. Meaning: a disciplined, tool-heavy, centralized way to organize many programmers.

**2. Product-line model — Microsoft Software Factories (Greenfield & Short, 2003–2004).** "A software factory is a product line that configures extensible development tools like Microsoft Visual Studio Team System (VSTS) with packaged content and guidance, carefully designed for building specific kinds of applications. A software factory contains three key ideas: a software factory schema, a software factory template and an extensible development environment" ([Moving to Software Factories, Microsoft archive](https://learn.microsoft.com/en-us/archive/blogs/askburton/moving-to-software-factories-2)) **[fact]**.

- The **schema** is "a recipe": it lists the ingredients (projects, directories, configuration files) and "explains how they should be combined".
- The **template** is "like a bag of groceries containing the ingredients listed in the recipe" — patterns, guidance, templates, frameworks, tools.
- The book's formal definition, as quoted on a [Microsoft-hosted blog](https://learn.microsoft.com/en-us/archive/blogs/jezzsa/faq-what-is-a-software-factory): "a software product line that configures extensible tools, processes and content using a software factory template based on a software factory schema to automate the development and maintenance of variants of an archetypical product by adapting, assembling and configuring framework-based components."

The OOPSLA 2003 paper and the book itself were not readable here (ACM returned 403) **[unverified beyond the quotes above]**. The idea shipped as patterns & practices factories on the Guidance Automation Toolkit — for example the [Web Service Software Factory](https://learn.microsoft.com/en-us/archive/msdn-magazine/2006/december/service-station-web-service-software-factory). The [Smart Client Software Factory download](https://www.microsoft.com/en-us/download/details.aspx?id=572) is marked retired, and no current Microsoft product continues the line **[fact, from search results plus the retired download page]**.

**3. Platform model — US DoD and Air Force.** The [DoD Software Modernization Strategy (Feb 2022)](https://media.defense.gov/2022/Feb/03/2002932833/-1/-1/1/department-of-defense-software-modernization-strategy.pdf) (via Wayback) defines it: "A software factory is a software assembly plant for development and integration that contains multiple pipelines, equipped with a set of tools, process workflows, scripts, and environments, to produce a set of software deployable artifacts with minimal human intervention. It automates the activities in the develop, build, test, release, and deliver phases and supports multi-tenancy." The strategy names Air Force Platform One among enterprise factories and asks to "vet commercial tools once … make them instantly available through an enterprise-like repository" **[fact]**.

- The [DoD Enterprise DevSecOps Fundamentals v2.0](https://dodcio.defense.gov/Portals/0/Documents/Library/DoDEnterpriseDevSecOpsFundamentals.pdf) (via Wayback) adds that "a software factory must be designed for multi-tenancy and automate software production for multiple products". Each factory is "instantiated from hardened IaC code and scripts or DoD hardened containers from the sole DoD artifact repository, Iron Bank", and cloud templates reduce mission-owner security work "by leveraging inheritance" **[fact]**.
- Platform One lists "Software supply chain security (Iron Bank) DevSecOps infrastructure (Big Bang) Managed Platform as a Service (Party Bus)" (software.af.mil, Wayback Jan 2025). Kessel Run is "an Air Force unit that delivers resilient command and control and targeting software capabilities" (kesselrun.af.mil/about, Wayback) **[fact]**.
- [GAO-23-105611](https://www.gao.gov/products/gao-23-105611) describes the "software factory ecosystem" as "a collection of tools and processes that support activities throughout the DevSecOps life cycle" **[fact]**.
- What is central versus per program **[inference from the above]**: hardened components, vetted tools and inheritable security controls are central; each mission team assembles its own pipelines and owns its code and its share of the authorization.

**4. Agent model — AI software factories (2025–2026).** The term now means an automated SDLC loop in which agents triage, specify, implement, review and verify, with humans at chosen gates. First-party examples, and where each one lives relative to the target repository **[fact]**:

**Which sense the owner means [inference].** "One set of base ideas and opinions applied to many projects" is the **product-line** sense (a schema/template configuring tools, process and content for a family of products) combined with the **platform** sense (central hardened components plus per-team instantiation and inherited controls). "Agents triage, spec, implement, review" is the **agent** sense. Workbench can be all three only if it keeps them apart: the opinions are the product-line layer; GitHub and the Developer's machine are the platform; the run contracts in ADRs 0014–0023 are the agent loop. The current AI products split exactly on the in-repo-versus-central question (table above). The ones aimed at many repos — Warp Factories, Mastra, oz-for-oss — run a hosted control plane, which Workbench's ADR 0005 and 0013 rule out.

## The talk's model — Zach Lloyd, "Software Engineering Is Becoming Factory Engineering"

**Provenance [fact].** Video metadata via `yt-dlp` (title, uploader, date): "Software Engineering Is Becoming Factory Engineering — Zach Lloyd, Warp", channel _AI Engineer_, uploaded 2026-09-27, 20:36 long. The English transcript was retrieved on 2026-11-04 with [`youtube-transcript-api`](https://github.com/jdepoix/youtube-transcript-api) (YouTube's auto-generated captions; `yt-dlp` subtitle download was rate-limited with HTTP 429). Auto-captions contain transcription errors and the slides are not in the transcript, so diagrams the speaker points at ("you're not supposed to read this") are known only by his description. The repository behind the closing QR code is not named in the audio; [`warpdotdev/oz-for-oss`](https://github.com/warpdotdev/oz-for-oss) matches the description (triage and spec agents on Warp's agent platform) but is **unconfirmed**. The YouTube upload date is the only date verified here; it may not be the date the talk was given. Timestamps below are `mm:ss` into the video; quotes are verbatim from the captions.

**Thesis.** Software engineering "is going to become something more like factory engineering" (01:33–01:47). Development moved from chat/autocomplete to interactive agents, and over the next "6 months, a year" moves "much more towards a world of automation" (01:49–02:25).

**The factory is the SDLC as a loop (03:17–04:07).** "Every project of significant size, I believe, is going to have something like this." The loop: ideas come in → agents triage → agents write a spec when the work is complicated → **human reviews the spec** → agents implement → **human and agent review the code** → agents verify → **human reviews the product** → ship → monitor → back to the top. The human steps are drawn as "little blue boxes". "This loop says a cloud software factory. This loop could literally just say like the software development life cycle. It's the same thing."

**Why Warp built one: open source (04:21–07:48).** Warp open-sourced its product partly "to build a public factory" — `build.warp.dev`, which "shows all of the issues that are flowing through our system and what state they're in, what agents are working on them, what contributors are working on them", a "proto-factory done at scale" (04:32–05:01). The traditional pains of open source — noisy issues, sloppy PRs, "code review hell", verification effort — became manageable because they "built a whole set of automations, really a software factory, around managing the open source project" (07:12–07:46).

**Components (07:58–08:22).** "A set of automations", "a way of providing context and skills", "a way of bringing humans in at the correct time … when things get stuck on the factory", and "some set of self-improvement capabilities … think of this as loops". "There's nothing special about open source here … every company, every open source project will have at its core a software factory kind of like the way that CI/CD became just like oh of course you have that" (08:37–08:59).

**The factory floor (09:00–12:02).** A "graph of steps where you are defining like okay, how does software get built for my product? And it looks pretty similar for every product" (09:12–09:24).

| Stage          | What the talk says                                                                                                                             | Time        |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| Inputs         | Ideas from team or users via channels: task tracker, Slack/Teams, terminal/IDE, monitoring                                                     | 09:34–10:02 |
| Triage         | An agent reads incoming issues; "if this is easy and this is unambiguous, just implement it" — "how you can actually get going with a factory" | 10:03–10:23 |
| Spec           | For hard issues, an agent writes a **product spec** ("product invariants") and a **tech spec** ("architecture and the shape of the code")      | 10:23–10:54 |
| Implement      | "A coding agent that runs somewhere in the cloud. It makes a diff."                                                                            | 10:54–11:03 |
| Review         | "In many ways the most painful part"; agent review first, then "a risk management exercise of like when do you bring in humans"                | 11:03–11:27 |
| Verify         | For UI apps, computer use producing videos and screenshots                                                                                     | 11:28–11:43 |
| CI/CD, monitor | "Still use it, obviously"; agents observe what shipped ("Is it crashing? Is it being used?") and feed the top of the loop                      | 11:43–12:02 |

**Build versus buy (12:04–12:36).** A simple version is easy to build (Uber built an internal one), but "to build a thing that actually scales … you should probably [be] focusing on your own product not building this infrastructure".

**Reference architecture (12:36–13:24).** Intake channels on top; "a sort of control plane for figuring out how work gets distributed across your factory floor"; "cloud sandboxes" where work happens; a choice of harness and model; and "some kind of data plane that sits below your factory … that lets agents remember what they've done, learn, improve over time".

**Measure and improve (13:24–14:48).** "The factory is not just like a product. It's also a mindset": measure how much software shipped against "human time and token time". Self-improvement is a **skill loop**: factory agents run skills; "observer agents" watch how the skills are applied and improve them — e.g. if senior engineers keep correcting a code-review agent's comments, an observer improves the review agent "for the next run" (14:16–14:44).

**Engineers (14:48–16:12).** "You're not just building the product, but you're building the thing that builds the product" — "process engineering or manufacturing", "meta engineering".

**Q&A (17:02–20:10).** Asked about the tension between "don't build this" and being a factory builder: "everyone's going to deploy some sort of factory, but then the tuning of the factory, the like, are these the right skills for my domain? Is this factory building my product in the right way?" is where the engineering interest lies (17:12–17:48). On taste: the factory metaphor "can kind of sound like … dehumanizing"; "human taste, human input, human product sense, humans like guiding at those touch points where you can't automate stuff is absolutely like essential" (19:26–20:02).

**Reading of the model [inference].** Three things matter for Workbench:

1. The talk's unit is **one factory per project** ("every project of significant size"), but the floor is **the same graph for every product**, and the per-project work is **tuning** — skills for the domain, where humans step in. That is a shared-platform-plus-per-project-configuration shape, not "one bespoke factory per repo" and not "one undifferentiated factory for all repos".
2. Its architecture is **cloud-hosted** (control plane, cloud sandboxes, data plane) and its improvement loop needs **content** (review comments and their corrections) to flow to observer agents. Both pull against Workbench's local seam (ADR 0005) and "numbers about activity, never content" Telemetry posture (CONTEXT.md, ADR 0001/0013).
3. The speaker's own product, [Warp Factories](https://docs.warp.dev/factories) (launched August 2026 per its docs), makes the shape explicit: a factory definition (`factory.yaml` with agents, skills and automations) lists the `repositories` it serves and is "either managed by Warp or stored in a GitHub repository your team owns" — **a central definition pointing at many repos**, not an install inside each repo **[fact for the quote; inference for the reading]**.
4. Its human gates match Workbench's existing ones closely: spec review ≈ approved Issue brief (ADR 0014), code review ≈ human merge instruction (ADR 0011), verification ≈ Verification recipe/evidence (ADR 0021). The talk is silent on authority, approval binding, credentials, or what happens when a run's outcome is unknown — the areas Workbench's Factory 03–10 decisions cover in depth.

## Workbench today

All statements in this section are **[fact]** from the repository at `1c71882` unless marked otherwise.

### How it is added to a project

- **Package dependency.** The host adds `@quick-release/workbench` (public npm per [ADR 0013](../adr/0013-public-access-distribution.md), or `github:Quick-Release/workbench#semver:^0.1.0` from release tags) and a `"workbench": "workbench"` script ([README](../../README.md#install-it-in-a-host-repository)). The host's lockfile pins the version; upgrades are `pnpm up` or a dependency bot. The package ships source plus its own toolchain (`vite-plus`, React, Effect) as runtime `dependencies` ([package.json](../../package.json); the reasoning is in [versioning-and-distribution.md §4](./versioning-and-distribution.md)).
- **Host detection.** `bin.mjs` runs `scripts/commands/sync-data.mjs` from `WORKBENCH_SOURCE_ROOT` or the cwd, and `scripts/host/source-root.mjs` resolves the host as override → superproject → git toplevel → cwd. Any enclosing checkout that is not Workbench's own counts as the host. The README already documents `WORKBENCH_SOURCE_ROOT` for "standalone checkouts, global installs, relocated package stores": **today Workbench can already run without being a dependency of the repo it serves**, but that path is not the documented default.
- **Config.** `workbench init` (`scripts/commands/init.mjs`) writes `workbench.config.json` at the host root, validated by `workbench.config.schema.json`: `projectName`, `repositoryUrl`, `theme`, `services[]` (asana/notion/github/gitlab adapters with `tokenEnv`), `sessions`, `clarification`. The file is **gitignored in Workbench's own repo** (`.gitignore:14`), and the README describes copying the example into the host; nothing says whether a host should commit it.
- **Generated state.** The snapshot `src/data.generated.ts` is written inside the installed package directory ([versioning-and-distribution.md §4.1](./versioning-and-distribution.md)). Owned-clarification run records go to `<host>/.workbench/clarification/runs.sqlite` (`scripts/seam/clarification/runtime.mjs:120`; `.workbench/` is gitignored). [Factory 07](./factory-durable-run-ownership-and-recovery.md#storage-migration-and-retention-posture) wanted the operational store "outside the installed package and working tree, keyed by canonical repository identity rather than path"; the current location is inside the working tree — a small, existing tension with that note **[inference]**.
- **Secrets and reporting.** Tokens live in a gitignored `.env` loaded by dotenvx. Company Telemetry is active only where internal provisioning supplies `TELEMETRY_INGEST_URL`/`TELEMETRY_INGEST_TOKEN` (`scripts/sync/telemetry.mjs:139–140`; [ADR 0001](../adr/0001-mandatory-telemetry-internal-tool.md), [ADR 0013](../adr/0013-public-access-distribution.md)).

### Constraints any adoption model must respect

- **One install, one host repo** — CONTEXT.md "Host repo"; restated in ADR 0005 ("Hosted backend — rejected: one install serves one host repo, locally"), ADR 0014 (pilot: "one trusted GitHub host repo per install"), and #125/#173 ("One host repo per install remains the scope"; "each install still serves one host repo").
- **Localhost seam** — the browser talks only to localhost `/api/*`; behind it run only tools a Developer would run by hand; no hosted backend ([ADR 0005](../adr/0005-control-surface-localhost-seam.md)).
- **Canonical host-repository identity is load-bearing in the factory contracts.** Run records ([ADR 0020](../adr/0020-durable-run-ownership-and-reconciliation.md)), Verification recipes and evidence ([ADR 0021](../adr/0021-independent-verification-and-revision-bound-evidence.md)), Publication intents and Delivery profiles ([ADR 0022](../adr/0022-safe-idempotent-draft-pr-publication.md)) all bind to one canonical host repository. Approvals are per repository; nothing in them assumes a shared multi-repo authority.
- **Public distribution** — one codebase, anyone can install and run it against their own repo, company flows dormant by omission, no public endpoint ([ADR 0013](../adr/0013-public-access-distribution.md)).
- **Telemetry posture** — identified numbers about activity, never content; content leaves the machine only by explicit Submission; Session capture is separate opt-in (CONTEXT.md "Reporting"; ADR 0001).
- **Credential boundary** — runtimes never get generic credential access ([ADR 0016](../adr/0016-clarification-threat-model-and-credential-boundaries.md)); remote execution is an unresolved optional topic ([#174](https://github.com/Quick-Release/workbench/issues/174)), and the multi-repo ecosystem was left as explicit fog in the [skills-ecosystem chart](../wayfinding/skills-ecosystem-dashboard.md).

**Reading [inference].** Workbench already _is_ a hybrid in practice — central code with per-repo data — but the central half has no name or version of its own (it is "whatever this Workbench release and upstream HEAD say"), the per-repo half is **copied** rather than **referenced**, and the most important opinions for a factory (gates, review rules, CI, branch protection) are not part of what is distributed at all. That, more than in-repo-versus-central, is what makes the current model feel wrong for "apply our opinions to many projects".

The Copier docs describe the update algorithm but do not use the term "3-way merge".

**What the survey implies for Workbench [inference].**

1. **Two families.** _Live-reference_ layers (rulesets, `.github` defaults, branch-ref reusable workflows, untagged presets, managed settings) cannot drift but change every repo at once without review. _Vendored_ layers (Copier, cruft, projen, Nx, `skills` CLI) are reviewable and pinned, but each needs an explicit drift answer — a 3-way update, read-only generated files, a CI `check` exit code, or a frozen lockfile. Workbench today is vendored without any drift answer.
2. **The common hybrid is a thin manifest that records "which central opinion, at which version".** Examples: `uses: …@sha`, `extends: github>org/x#v2`, `.copier-answers.yml`, `.cruft.json`, `.projenrc` + package version, `enabledPlugins`, `skills-lock.json`. Upgrades arrive as a reviewable bump PR.
3. **Override semantics should be chosen per kind of opinion.** Gates (branch protection, required checks, review rules) fit _additive / most-restrictive-wins, not overridable_ — GitHub rulesets already do this without any repo file. Conventions (label names, docs, skills) fit _repo may override, override is visible_.
4. **Enforcement and distribution are separate planes everywhere.** GitHub separates rulesets from templates/reusable workflows; Claude Code separates managed settings from marketplaces. Workbench should not try to be the enforcement plane — it runs as the Developer, locally, and ADR 0011 already notes GitHub cannot encode the human merge instruction. It can _observe_ enforcement and _propose_ conformance.

## Options compared

"Repo-agnostic" hides two separate questions that should be decided separately **[inference]**:

**Why not B now [inference].** B is the talk's architecture and the most natural reading of "factory", but every accepted constraint above points against it: it reverses ADR 0005, needs multi-repo authority in contracts designed around one canonical repository (0020–0022), cannot ship in the public product without a service (0013), and would move content off the machine (0001/0013). The parts of B that are valuable — one place to change the opinions, a view across repos — can be had without a shared runtime. If remote or always-on execution is wanted later, [#174](https://github.com/Quick-Release/workbench/issues/174) is the place, and it already says the seam must not become a hosted multi-tenant service.

**Why not stay with A [inference].** A works for one repo. For many repos it has no answer to "which version of our opinions does repo X follow, and how far has it drifted?", it distributes none of the gates, and it installs skills from upstream HEAD with the latest CLI rather than from a company-pinned set.

## Recommendation

**Adopt option C, and keep the two halves explicit [proposal]:**

> **Opinions are central and versioned; adoption is declared per repo; the runtime stays local and serves one host repo at a time.**

Concretely:

1. **A Factory baseline, published centrally and versioned.** One artefact holds the company's opinions: workflow phases and label strings, triage roles, client labels, board placement; the skill set with sources and pinned refs/hashes; skill-flow classification; the conventions docs `setup-matt-pocock-skills` produces today; recommended gates (required checks, branch-protection/ruleset shape, PR template, review rules from ADR 0011); and defaults for run profiles, Verification recipe templates and Delivery profile templates. Initially it can live in Workbench's own repository and ship inside the npm package — the defaults in `scripts/tracker/labels.mjs` and `src/data/skill-flow.mjs` already _are_ an unnamed baseline. Splitting it into its own package or repo is warranted only once a second baseline (another team, or a public user's own) is real.
2. **A committed Baseline adoption in each host repo.** Extend `workbench.config.json` (or add a sibling file) with `baseline: { id, version }` and declared deviations — e.g. a host keeping its own label names. Commit it. This is the `.copier-answers.yml` / `extends: …#v2` / `enabledPlugins` role. Host-specific data stays where it is: tracker and service config, `CONTEXT.md`, `docs/adr/`, `docs/research/`, the skills lockfile.
3. **Conformance is read-only and visible.** A `workbench doctor` (the [#125](https://github.com/Quick-Release/workbench/issues/125) Host Repo Doctor, given a baseline to compare against) reports ready / missing / drifted / unknown per opinion: tracker labels, skills lockfile versus baseline pins, conventions docs, rulesets/branch protection, CI check names. It works like `cruft check` and `skills check`, and can run in a host's CI. It never mutates — consistent with ADR 0005's "tools a Developer would run by hand" and #125's "the doctor itself is read-only".
4. **Upgrades are reviewable PRs, not silent changes.** Bumping the baseline version (by a dependency bot bumping the package, or `workbench upgrade`) produces a proposed diff to the host — docs, skill pins, label creations/renames as an explicit list — for the Developer to approve, like `copier update` or `nx migrate`. Writing that PR is an action through the seam with confirm-first semantics. The Factory 09 Publisher contract (ADR 0022) is the long-term home if it should be agent-assisted.
5. **Hard gates are enforced by the platform, not by Workbench.** The baseline _describes_ the required ruleset; the org applies it with [GitHub organization rulesets](https://docs.github.com/en/organizations/managing-organization-settings/creating-rulesets-for-repositories-in-your-organization) (targeted by repo property, no per-repo file, most-restrictive-wins) and, if wanted, a [reusable CI workflow](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows) pinned by SHA. Workbench observes and reports. This also closes the gap Factory 01 noted: gates currently don't travel to other hosts at all.
6. **Installation is decoupled from serving.** Keep the npm dependency as the supported path for Node hosts — the lockfile pin and dependency-bot upgrades are worth having. Also document the machine-level path that already works (`npx @quick-release/workbench` or a global install, with `WORKBENCH_SOURCE_ROOT`) for non-Node hosts, which #125 requires. In both cases one running instance serves one host repo. The adoption record states the minimum Workbench version the baseline needs, so a machine-level install can refuse or warn on mismatch.
7. **Many repos is a view, not a tenancy model — later, and only if asked for.** If the owner wants a cross-repo picture ("which repos are on baseline 3, which have drifted, where is review backing up"), the honest first step is a local, read-only portfolio that reads several hosts' adoption records and doctor reports. Internal installs could also report baseline id/version and conformance counts as Telemetry — numbers, not content. Neither makes one install serve many repos for _actions_; that would reopen ADRs 0005 and 0020–0022 and belongs with [#173](https://github.com/Quick-Release/workbench/issues/173)/[#174](https://github.com/Quick-Release/workbench/issues/174).

**Trade-offs accepted [inference].**

- Upgrades need a human review per repo. This is deliberate and in line with ADR 0011, but slower than a live reference. Fast-moving rules belong in the live plane (rulesets), slow-moving conventions in the vendored plane.
- Two places to look: the baseline for "what we believe", the host for "what this repo does and why it deviates". The doctor exists to join them.
- A versioned baseline is another release artefact to maintain. Bundling it in the Workbench package first keeps the cost close to zero.
- The talk's cloud control plane, cloud sandboxes and content-fed skill-improvement loop stay out of scope. A local equivalent of the skill loop is possible: an observer proposes a skill or baseline change from the Developer's own corrections as a reviewable PR to the baseline repo. That would be a separate decision about Session capture and Content-sourcing boundaries, not Telemetry.

## Concept changes needed (proposals)

**Does the concept need to change? [inference]** Partly. The product posture — a local control surface over one host repo, with the Factory 01–10 authority chain — holds up against the talk and the established meanings. What is missing is a **first-class, versioned home for the opinions** that make it a _factory_ rather than a dashboard, and a name for "this repo follows those opinions at version N". Today CONTEXT.md describes Workbench only as "a local dashboard that renders a host repo's planning … work"; the factory role is implicit.

Proposed CONTEXT.md terms **[proposal — not edited]**:

| Term                   | Proposed definition                                                                                                                                                                                                                                                                                                                                    | Avoid                                                                                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Factory baseline**   | The versioned, centrally published set of opinions Workbench applies to host repos: workflow and triage vocabularies and label strings, skill set and pins, skill-flow classification, conventions docs, described gates and review rules, and default run, verification and delivery templates. A baseline is data, never authority to act on a host. | standard (implies enforcement), preset (tool-specific), profile (taken by Capability/Execution/Delivery profile), template (implies one-shot copy) |
| **Baseline adoption**  | A host repo's committed declaration of which Factory baseline (id and version) it follows and which deviations it declares. A property of the host repo.                                                                                                                                                                                               | manifest (already used for the data-flow and pre-start manifests), lockfile                                                                        |
| **Baseline drift**     | An observed difference between a host repo's Baseline adoption and its actual tracker, skills, docs or gate state. Declared deviations are not drift.                                                                                                                                                                                                  | non-compliance (implies enforcement Workbench does not have)                                                                                       |
| **Conformance report** | The read-only, per-opinion ready / missing / drifted / unknown result of comparing a host repo against its Baseline adoption. The existing **Host repo** entry would gain one sentence: _"A host repo adopts a Factory baseline; the install still serves exactly one host repo."_ That keeps the single-host invariant explicit instead of letting "factory" imply multi-tenancy.

Candidate ADRs **[proposal]**:

1. **"Opinions ship as a versioned Factory baseline; hosts declare adoption; the runtime stays single-host."** Records option C, rejects B (hosted/multi-tenant) and A-as-is, and names which opinion kinds are _live-enforced_ (org rulesets) versus _vendored-with-review_ (docs, skills, labels).
2. **"Baseline upgrades arrive as reviewed host changes; conformance diagnosis is read-only."** Upgrade semantics, override rules per opinion kind, label-migration safety (never auto-rename or delete labels), and how `docs/agents/workflow-labels.md` overrides interact with baseline versions.
3. **"Gates are enforced by the platform; Workbench observes them."** Amends ADR 0011's consequences for multi-repo use: the ruleset is the distributed gate, Workbench's doctor checks it, and the human merge instruction stays procedural.
4. **Possibly, later:** whether internal Telemetry gains a baseline-id/version and conformance-count dimension (an ADR 0001 amendment, numbers only), and whether a local multi-repo portfolio view is in scope — the "multi-repo ecosystem" fog in the skills-ecosystem chart.

## Open questions — suggested answers

Each question below has a suggested answer **[proposal]**, the reasoning behind it, and what would change the answer. Facts about the org were checked on 2026-11-04 with `gh`:

- **[fact]** `Quick-Release` is on the GitHub **Team** plan.
- **[fact]** It has about 101 active repositories. By primary language: 35 PHP, 26 TypeScript, 14 JavaScript, 5 Astro, 5 MDX, and the rest Shell, HTML, CSS or none.
- **[fact]** Exactly one host repo depends on the package today: `cesam-astro`, with `"@quick-release/workbench": "^0.2.1"` in `package.json`. It has no committed `workbench.config.json` at its root.

The owner accepted all eight suggested answers on 2026-11-04. They are recorded in ADRs 0024 (items 1, 2, 3, 5, 6, 8), 0025 (upgrades and conformance) and 0026 (item 4). Item 7 is the rejected option in ADR 0024.

### 1. Whose opinions? — One company baseline, kept inside the Workbench package

**Suggested answer.** Ship one baseline, `quick-release` (versioned with the package), as a module inside `@quick-release/workbench`. Design the `baseline: { id, version }` field so that `id` could later name another package or Git ref. Don't build that resolver now.

**Why.**

- There is one adopting host today, and one opinion owner.
- A separate baseline package would add a second release train and a compatibility matrix before anyone needs one.
- Public users (ADR 0013) get the company baseline as the default. They can deviate per opinion, which is question 2.
- This matches step 1 of the migration table and the note's own "split only once a second baseline is real".

**What would change it.** A second team, or a real public user, asking to publish their own opinions. That is the point to extract the module into `@quick-release/factory-baseline` and resolve `id` through npm or a Git ref, the way Renovate resolves `extends` presets.

### 2. Overrides — conventions are overridable and visible; gates are not

**Suggested answer.** Each opinion kind gets an override class, listed in the baseline itself:

| Opinion kind                                                     | Override class                       | How a host deviates                                                                                                                           |
| ---------------------------------------------------------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Label strings, triage role names                                 | **Renameable**                       | Map baseline role to host label in the adoption record. The role set itself is fixed, because the frontier and run logic depend on it.        |
| Workflow phases                                                  | **Fixed**                            | None. Phases are part of the run model (ADRs 0007, 0010).                                                                                     |
| Skill set                                                        | **Additive, with declared removals** | A host may add skills freely. Removing a baseline skill is a declared deviation with a reason. The doctor shows it, it doesn't flag drift.    |
| Skill pins                                                       | **Pinned by baseline**               | A host may pin newer for a trial, as a declared deviation. Older than the baseline is drift.                                                  |
| Conventions docs (`docs/agents/*`)                               | **Overridable**                      | Host edits are allowed. The doctor diffs them against the baseline template and reports "customised", not "drifted".                          |
| Gates (protected `main`, required checks, human merge, ADR 0011) | **Not overridable**                  | None in the adoption record. An exception is made by changing the org ruleset's targeting (a custom property), which is visible at org level. |

**Why.**

- The run machinery (ADRs 0008, 0010, 0020–0023) depends on roles and phases, not on the exact label strings. So strings can move and the role set can't.
- Gates are the one thing whose weakening has to be visible to someone other than the repo's own developer. Keeping them out of the adoption file means a repo can't quietly opt out of review.

**What would change it.** A client project contractually needing a different review flow. That should be a separate baseline id, not an override.

### 3. Is `workbench.config.json` committed? — No; put the adoption record in a separate, committed file

**Suggested answer.** Keep `workbench.config.json` local and gitignored. Add a committed `.workbench/baseline.json` holding only `{ "baseline": { "id", "version" }, "deviations": [...], "minWorkbenchVersion" }`.

**Why.**

- **[fact]** The config mixes kinds of data. `workbench.config.example.json` has per-Developer settings (`sessions.enabled`, `clarification.provider` and `dataDestination`, `theme`) next to host data (`projectName`, `services[]` with ids and `tokenEnv` names).
- Committing that file forces one Developer's opt-ins on everyone. That runs against the opt-in postures of Session capture and clarification (ADRs 0014, 0016).
- A dedicated file is small, reviewable, and easy for bots and the doctor to parse. It's also the same role `.copier-answers.yml` plays.
- `.workbench/` already exists as Workbench's directory in the host. Committing one file in it needs a gitignore negation (`.workbench/*` plus `!.workbench/baseline.json`), so `workbench init` should write that rule.

**Follow-up.** Host-shared, non-secret fields such as `projectName` and `services[].id` could move into the committed file later. Keep that separate from this decision.

**Related tension.** The note found that clarification state lives under `.workbench/` in the checkout, while Factory 07 wanted it outside the working tree. Committing `.workbench/baseline.json` makes that directory partly tracked. That is one more reason to move run state out to a machine-level store (for example `$XDG_STATE_HOME/workbench/<repo-id>/`) when Factory 07 is implemented.

### 4. Enforcement appetite — start descriptive plus doctor; adopt org rulesets after a one-repo trial

**Suggested answer.** In order:

1. The baseline describes the gate set. The doctor checks each host's branch protection and rulesets through the API.
2. Trial one org ruleset, targeted by a custom property such as `factory=quick-release`, on `workbench` and `cesam-astro`.
3. Widen it once the trial passes.
4. Hold the shared reusable CI workflow until there's a second Node host. There's nothing to share yet.

**Why.**

- **[fact]** GitHub's docs say rulesets are available "for customers on GitHub Team and GitHub Enterprise plans" ([about rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets), [creating org rulesets](https://docs.github.com/en/organizations/managing-organization-settings/creating-rulesets-for-repositories-in-your-organization)).
- **[fact]** But the same "about" page also says: "For organizations on the GitHub Enterprise plan, you can set up rulesets at the organization level to target multiple repositories." The docs conflict on whether one org ruleset can target many repos on Team.
- **[fact]** Custom-property targeting is documented with no plan limit stated.
- **[unverified]** Whether "require workflows to pass" is available on Team wasn't confirmed.
- The `gh` token used here lacks `admin:org`, so the org's current rulesets couldn't be listed.
- So the trial in step 2 is how to settle the plan question, rather than designing around a feature that may not exist on Team.

**Fallback if org-level targeting turns out to be Enterprise-only.** Apply the same ruleset per repo with a small script (`gh api repos/{repo}/rulesets`) that the doctor verifies. It's less elegant but uses the same model.

### 5. How many repos, how soon? — Consistency first; defer the cross-repo view

**Suggested answer.**

- Next quarter's target: every repo that adopts Workbench passes its doctor against the current baseline.
- Don't build step 7, the portfolio view, yet.
- Do add the cheap part of step 7 now: on internal installs, report the baseline id and version plus conformance counts as Telemetry. That's numbers only, within ADR 0001.

**Why.**

- **[fact]** One host has adopted Workbench, out of about 101 active repos.
- A portfolio view of one repo answers nothing.
- The Telemetry dimension gives a cross-repo picture ("which installs are on which baseline, how many checks fail") for almost no cost, and doesn't touch the single-host model.

**What would change it.** Adoption passing about five hosts, or someone needing to ask "where is review backing up across repos". At that point, build the local read-only portfolio view.

### 6. Non-Node hosts — Yes; make the machine-level install a first-class path

**Suggested answer.**

- For hosts without a `package.json`, support `npx @quick-release/workbench@<version>` or a global install.
- `.workbench/baseline.json` carries `minWorkbenchVersion`. Workbench refuses to start below it, and warns when it's more than one minor version ahead.
- Node hosts keep the dev dependency, for the lockfile pin and bot-driven upgrades.

**Why.**

- **[fact]** 35 of about 101 active repos are PHP (WordPress themes, plugins and services), and several more are Shell or HTML.
- If the factory is meant for all projects, the non-Node path can't be second-class. #125 already requires it.
- The version floor in the adoption record replaces the pin that a lockfile gives Node hosts.

**Follow-up.** Renovate can't bump a version inside a custom JSON file without a regex manager. The baseline should ship a Renovate preset with that manager, so non-Node hosts get upgrade PRs too.

### 7. The talk's direction — No cloud factory now; borrow the loop, not the hosting

**Suggested answer.** Don't grow toward the talk's hosted control plane in this decision. Take three of its ideas that fit the local model:

1. **The same loop everywhere, tuned per project.** That is the baseline plus the adoption record.
2. **"Are these the right skills for my domain?"** That is per-host skill additions plus the doctor.
3. **Factory improvement as reviewed changes.** That is baseline upgrades as PRs, and later skill-improvement proposals as PRs to the baseline.

Keep #174 (remote runners) as the single entry point if hosted execution comes back on the table.

**Why.**

- Each part of the cloud version runs into an existing decision: ADR 0005 (localhost seam), ADR 0013 (public posture), ADR 0016 (credential boundaries), and ADR 0001's "numbers, never content".
- Reopening all four is a product change. It deserves its own grilling, not a side effect of an adoption-model decision.

**What would change it.** Needing unattended runs while no Developer machine is on, or runs in parallel beyond one machine (#173). Both are execution questions, and the baseline model works the same under either.

### 8. Skill provenance — Pin upstream at reviewed refs now; fork only on divergence

**Suggested answer.**

- The baseline pins `mattpocock/skills` and `Effect-TS/skills` to reviewed commit SHAs, recorded in the baseline and in host `skills-lock.json` files.
- Company-specific skills, such as the ones in this repo's `.claude/skills/`, go into a company skills source that the baseline also pins.
- Fork an upstream skill only when it needs a local change that upstream won't accept.
- Package everything as a Claude Code plugin marketplace only once a non-Claude agent is no longer part of the workflow. Codex and Pi also run here (see AGENTS.md and ADR 0018), so for now a format-neutral skills source fits better than a Claude-only marketplace.

**Why.**

- **[fact]** Today's install runs `skills@latest … --all` from upstream HEAD (`scripts/seam/routes/skills-api.mjs:27,32`). Hosts set up a week apart can get different skills.
- Pinning fixes that at almost no cost.
- Forking takes on maintenance and loses upstream fixes, so it should be reserved for real divergence.
