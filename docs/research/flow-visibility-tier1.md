# Flow visibility, Tier 1: the phase board, the live board, and time-in-phase

**Date:** 2026-09-10
**Sources:** primary only — this repository's source and planning docs (`CONTEXT.md`, `docs/agents/workflow-labels.md`, `docs/agents/issue-tracker.md`, `docs/adr/0005…0009`, `src/**`, `scripts/**`, read statically in the agent worktree; no `pnpm install`/`pnpm dev`/build was run), live read-only `gh api` probes against `Quick-Release/workbench` run on this date (issue events, issue timeline, rate-limit headers, issue/label counts — outputs quoted below, truncated), the GitHub REST API reference pages for issue events, issue timeline, rate limits, and REST best practices, and MDN's `visibilitychange` reference (all fetched live 2026-09-10). Anything I could not verify is marked as such.

## Question

Can Workbench give the team visibility over what sits on which step of the skills workflow, as three Tier 1 features — (1) a flow board whose columns are the workflow phases, (2) a live board that reflects label writes without manual sync clicks, and (3) time-in-phase ("4d in implementing") from phase-transition timestamps — and what is the shortest concrete build path for each against the code that actually exists?

## TL;DR

**All three are feasible with no new runtime dependencies; combined effort ≈ 5–8 dev-days.** The heavy lifting already exists: `workflow:*` label parsing with double-label → furthest-along resolution and warnings lives in `phaseFromLabels` (`scripts/tracker/labels.mjs:96-116`); the card's full derivation vocabulary (phase, triage, deferred, claimed, caveats, decision-ticket nulling) lives in `deriveDisplayState` (`src/lib/display-state.ts:38-84`); blocker/frontier math lives in `src/lib/frontier.ts:28-62`; a label-write action that is a near-exact template for a phase move already ships as `applyTriageMove` (`scripts/workflow-api.mjs:137-180`, `gh issue edit --add-label/--remove-label`). The board is therefore a new route + one pure helper + one seam endpoint.

Three verified facts shape the design. **(1) The board cannot show a meaningful shipped column today**: the tracker sweep reads open issues only (`scripts/tracker/issues.mjs:65-72`), closed items enter only as maps, map members, and blocker endpoints — and the live repo currently has 0 open issues, 60 closed, 21 wearing `workflow:shipped` (probe, 2026-09-10). A bounded closed+label query is required (ADR 0009 explicitly reserves "a bounded-label-query decision" for exactly this, `docs/adr/0009-decisions-and-artifacts-collect-at-sync.md:27`). **(2) "Live" has two legs**: `GET /api/workflow` serves the _file_ `src/data.generated.ts`, which only changes when `pnpm sync` runs, so a label written by a skill in a terminal becomes visible only after a sync; the browser-side atom reads the seam exactly once per page load (`src/hooks/use-workflow-state.ts:34-48`) and never polls. **(3) Time-in-phase is one `labeled`-event lookup per phase-labelled issue on GitHub's events endpoint**, verified live — and the probe surfaced a semantic trap: issue #79 wore `workflow:ticketed` and `workflow:implementing` _simultaneously_ for ~3.5 h (the skills add the next label without removing the previous), so `phaseSince` must be the latest `labeled` event for the _resolved_ phase's label, not the last label event overall.

---

## 1. Shared ground: how phase state moves through Workbench today

**The vocabulary.** Eight board columns map to the domain: pre-flow (no `workflow:` label — `docs/agents/workflow-labels.md:7`) plus the seven canonical phases (`src/types.ts:68-76`, mirrored server-side as `CANONICAL_WORKFLOW_PHASES`, `scripts/tracker/labels.mjs:8-16`). The sync script parses the _markdown table_ in `docs/agents/workflow-labels.md` as its vocabulary source (`workflowVocabularyFromMarkdown`, `scripts/tracker/labels.mjs:47-57`; wired at `scripts/sync-data.mjs:190-193`) — so column labels, skill writes, and the parser share one home, per ADR 0007.

**Phase resolution happens at record derivation, server-side, once.** `deriveWorkItem` (`scripts/tracker/labels.mjs:160-191`) turns a GitHub issue into a `WorkItemRecord` (`src/types.ts:102-114`, `src/schema.ts:96-108`): phase from labels (double labels → furthest-along **in vocabulary-table order** with a `GH-NN: …`-prefixed warning, `labels.mjs:107-115`), triage state, deferred, category, kind. Decision tickets keep their `kind` but the display layer nulls their phase (`src/lib/display-state.ts:35-36,77`) — their board placement must be derived in the view, because no code or doc today defines the kind→phase mapping (open question below). The double-label rule is ADR 0007's non-blocking-warning precedent (`docs/adr/0007-labels-encode-phase-and-kind.md:21`) and is already tested (`scripts/tracker.test.mjs:207-213`).

**The seam.** The dev server mounts `workflowApiPlugin` as a Vite/Connect middleware (`vite.config.ts:27`, `scripts/workflow-api.mjs:651-670`); there is no Express, no framework — just `guardedApi` + `sendJson` (`scripts/api-shared.mjs:20-39`). `GET /api/workflow` re-imports `src/data.generated.ts` behind an mtime-keyed cache (`workflow-api.mjs:50-66`) and validates through `parseWorkflowStatePayload` (`src/schema.ts:560-562`, `onExcessProperty: "error"`). Seven POST actions exist (`workflow-api.mjs:35-42,536-573`): triage move, issue edit/comment/create, edge add/remove, sync trigger. Every action shells out to `gh`/`pnpm` ("only the tools a Developer would run by hand", ADR 0005) and returns the re-read state, which the client pushes into the shared atom (`setWorkflowState`, `src/hooks/use-workflow-state.ts:32`).

**The two copies of every payload shape.** `src/types.ts` and `src/schema.ts` must change together: `parseOverviewData`/`parseWorkflowStatePayload` reject excess properties (`src/schema.ts:486-489,560-562`), so a field present in data but absent from the schema fails decode, and a field in types but not data fails `tsc` (the annotation trick at `src/schema.ts:486` makes drift a compile error). This confirms the convention recorded in `docs/research/agent-session-usage-page.md`. The third copy, `src/data.generated.ts`, is generated by `pnpm sync` and gitignored (`.gitignore`), so it is never hand-edited — but **13 test files** construct `WorkItemRecord`/payload object literals (grep over `*.test.{ts,tsx,mjs}` for `triageState:`, 2026-09-10), and a _required_ new record field touches each fixture helper.

## 2. Flow board (phase kanban)

**Verdict: feasible, mostly assembly. ~2.5–3.5 dev-days.**

### Route + nav wiring

TanStack Router here is file-based via the plugin (`vite.config.ts:22`); `src/routeTree.gen.ts` regenerates (`routeTree.gen.ts:7-9` warns against hand edits) and `src/router.tsx:1-17` needs nothing. **Name collision to respect**: `/flow` already exists — it is the _skill-catalog graph_ page (`src/routes/flow.tsx:15`), not a work-item board. Name the new route `/board`:

1. `src/routes/board.tsx` — copy the `triage.tsx` shape: `createFileRoute("/board")` with `validateSearch` for `?issue=` (panel param, `src/lib/issue-param.ts`) and optionally `?lens=deferred`; the route reads `useWorkflowState()`/`useWorkflowMode()` and hosts `<IssuePanelHost>` (`src/routes/triage.tsx:14-97` is the template end to end).
2. Nav: add `boardLink = linkOptions({ to: "/board", search: {} })` and a `NavItem`-union entry in `src/components/layout/nav-main.tsx:26-45,47-59`, then a row in `workflowItems` (`:66-74`) — spec #54's Workflow group "grows one destination per landing ticket", so this is the sanctioned extension point.
3. `src/components/BoardPage.tsx` + a renderToString smoke test beside it (the `triage.test.tsx` pattern).

### Derivation: a new `src/lib/board.ts`, reusing everything

One pure module beside the other derived-state helpers:

- Column for a regular issue: `deriveDisplayState(record, blocked).phase ?? "pre-flow"` — the helper already nulls decision-ticket phases and emits the five caveat kinds (`display-state.ts:38-84`).
- `blocked` per card: `openBlockers(record.id, blockerEdges, indexWorkItems(workItems))` (`src/lib/frontier.ts:23-42`) — exactly the wiring `TriagePage` already does (`src/components/TriagePage.tsx:169-173`).
- Frontier marking: recompute `frontier()` (`src/lib/frontier.ts:47-62`) or reuse `frontierStrip` (`src/lib/recommendation.ts:243-257`); a ticketed card whose id is in the frontier gets a "grabbable" chip. The header's recommendation chip (`src/components/layout/site-header.tsx:13-30`) and in-flight page (`src/components/InFlightPage.tsx:77-125`) prove the chip/badge vocabulary.
- Deferred: keep the card in its phase column with a "parked" chip behind a `?lens=deferred` filter — mirror triage's refused lens rather than inventing a ninth column (deferred is "orthogonal to both triage state and workflow phase", `CONTEXT.md:103-105`).
- Double-label warning per card: the resolution warning never reaches the browser today — `readIssueRecord` discards `deriveWorkItem`'s warnings (`workflow-api.mjs:112`), and `WorkflowStatePayload` carries no warnings (schema `src/schema.ts:167-174`) even though the server holds `snapshotCache.warnings` (`workflow-api.mjs:63`) and sync returns them only via the sync action (`SyncTriggerResult`, `src/types.ts:215-219`). Additive fix: a `warnings: readonly string[]` field on the payload (prefix-matched against `GH-NN:` at `labels.mjs:163`), or per-record `phaseWarning: string | null`. Recommended: payload-level `warnings` — one field, already produced, and the board filter is trivial.

**Decision-ticket placement is the one genuinely undefined piece.** Proposed mapping (flagged: _not found in any doc or code path — needs a decision before build_): `wayfinder:grilling` → grilling; `wayfinder:prototype` → prototyping; `wayfinder:research` → grilling (research feeds the decision conversation) or its own chip; `wayfinder:task` → implementing when claimed, ticketed when open-and-unclaimed; closed decision tickets → shipped column with a "decided" chip (their resolution _is_ the outcome; ADR 0009's Resolution concept). Alternative worth considering: render each map's decision tickets as a swimlane under the map card instead of forcing them into phase columns — `maps` and `ticketIds` order already ship in the payload (`src/types.ts:116-121`).

### Cards and moves through the seam

Cards render like `TriageRow` (`TriagePage.tsx:34-128`): id link opening the shared detail panel via `?issue=NN`, title, phase/triage badges, caveats in italic. The panel already offers comment/edit/create/edge actions through the shared wire grammar (`src/components/IssueDetailPanel.tsx:14-18`, `src/lib/issue-actions.ts:16-67`, runner `src/hooks/use-issue-actions.ts:15-54`) — a `phase-move` action slots in as a fifth kind so the panel _and_ the board share it.

Server-side, `IssueEditRequestSchema` does **not** cover labels (`src/schema.ts:192-197` — title/body/confirm only), and no phase-move endpoint exists. Add, cloned from the triage move:

- `PhaseMoveRequestSchema = { issueId, phase: WorkflowPhaseSchema }` / `PhaseMoveResultSchema = { message, issueId, phase, state }` (`src/schema.ts`, beside `TriageMoveRequestSchema:176-180`); mirror types in `src/types.ts:158-162`.
- `applyPhaseMove` in `scripts/workflow-api.mjs` beside `applyTriageMove:137-180`: `gh issue edit <n> --repo <repo> --add-label workflow:<target>` plus `--remove-label` for **every** worn `workflow:` label — the record only carries the resolved phase, so the server must remove both labels of a double-labelled issue (it can read the raw labels from the `gh issue view --json …,labels` read-back it already performs, `workflow-api.mjs:98-114`). Moving to pre-flow = remove all `workflow:` labels, add none. No `confirm` beat: ADR 0005 rules "label moves fire directly" (`docs/adr/0005-control-surface-localhost-seam.md:19`), and `docs/agents/workflow-labels.md:19` blesses hand moves. Register the route regex (`workflow-api.mjs:35-42`), the `POST_ROUTES` entry (`:536-573`), and `isWorkflowRoute` (`:646-649`).
- Static mode degrades to copy-the-command exactly like `staticMoveCommand` (`src/lib/triage.ts:79`): `gh issue edit <n> --add-label workflow:x --remove-label workflow:y`.
- Caveat: a hand move to `implementing` does not start `/implement`, and the skills themselves will re-write labels on their next run — the board move is a hand-move, GitHub history is the audit log (ADR 0005:19).

### The shipped column

**Verified gap.** `fetchOpenIssues` reads `state: "open"` only (`scripts/tracker/issues.mjs:65-72`); closed issues enter the payload only as map-labelled issues (`:77-90`), map members via targeted `fetchIssue` (`scripts/tracker/index.mjs:160-174`), or blocker endpoints (`:241-256`). Live probe (2026-09-10): 0 open issues, 60 closed, 21 closed wearing `workflow:shipped`, 37 closed wearing no phase label — and #65 sits closed at `workflow:reviewing`, #66 closed at `workflow:ticketed` (real `closed-without-shipped` cases; caveat exists at `display-state.ts:69-73`). So the shipped column renders ~nothing without new collection. Fix: a `fetchShippedIssues` paged walk beside `fetchMapIssues` — same `pagedIssues` helper (`issues.mjs:33-63`), `state: "closed", labels: "workflow:shipped"`, capped at 1–2 pages (100/page, `PER_PAGE:100` at `:7`) — the bounded-label-query shape ADR 0009 anticipates (`docs/adr/0009-decisions-and-artifacts-collect-at-sync.md:27`). Without a `closedAt` field on the record, "recently shipped" can only be "the newest 100 by the query's order" (default sort is created-desc) — acceptable for v1; a `closedAt`/`updatedAt` field is the clean upgrade (§4).

### Drag-and-drop vs buttons

**Recommend buttons (a "move to…" select), not DnD.** Verified: no drag-and-drop library exists in `package.json:40-68` (dnd-kit, react-dnd, react-beautiful-dnd all absent) and the repo's pattern is dependency-averse (graph note, `docs/research/graph-rendering-for-workbench.md`). The `NativeSelect` move (`TriagePage.tsx:106-124`) gives keyboard accessibility, testability via `renderToString`, and static-mode degradation for free; a board where moves are rare (a phase change is a session-level event, not a tidy-up) does not need drag's speed. Revisit DnD only after the board earns its keep.

**Risks:** column count (8) × card density on small screens — plan a responsive collapse (phases grouped: shaping grilling→ticketed / doing implementing→reviewing / done shipped); the undefined decision-ticket mapping (above); double-label warnings invisible without the payload `warnings` addition.

## 3. Live board

**Verdict: feasible; poll, don't push. ~1.5–2.5 dev-days including the server-side auto-sync loop.**

**How reads work today.** `GET /api/workflow` (`workflow-api.mjs:585-599`) → `loadWorkflowState` → the mtime-keyed `importSnapshot` (`:50-66`) — a `stat` per request and a free re-import unless the file changed; a localhost read is effectively free. The client, however, calls it **once**: `readLiveState` is guarded by `liveReadStarted` (`src/hooks/use-workflow-state.ts:34-48`), and after that the atom updates only from action results (`setWorkflowState`, `:32`). Nothing in `src/` polls. So the board is as stale as the last page load plus the last manual action.

**The two-leg problem.** The served payload mirrors `src/data.generated.ts`, rewritten only by `pnpm sync` (`scripts/sync-data.mjs:300-303`). A `workflow:*` label written by a skill in a terminal (the normal path per `docs/agents/issue-tracker.md:11`) never appears until a sync runs. "Live" therefore needs: (a) the browser re-reading the seam periodically, and (b) something re-running sync. Leg (a) is trivial. Leg (b) is the design decision.

**Polling vs SSE/WebSocket on this server.** The server is a Vite middleware, not a framework with a pub/sub story; SSE would mean a long-lived `text/event-stream` response hand-written into the Connect middleware, and `EventSource` would also _sidestep_ the ADR 0005 source scan, which only matches `fetch(` literals (`src/architecture.test.ts:25-37`) — the invariant's guard would need widening. Vite does ship a documented custom-event channel over its HMR socket (`server.ws.send` / `import.meta.hot.on` — not verified live in this note), which is the sanctioned push upgrade if one is ever needed. **Recommend plain polling for v1**: `setInterval` (15–30 s) inside `use-workflow-state.ts` re-running the existing `fetch("/api/workflow")` body, gated on `document.visibilityState` — MDN: the `visibilitychange` event fires when the user "switches tabs… minimizes or closes the browser", and hidden "is a good point at which pages can stop making UI updates and stop any tasks" (MDN, fetched live 2026-09-10); on `visible`, refetch immediately and restart the timer. Emit only when `meta` actually changed (see staleness below) to avoid re-render churn. The localhost GET costs nothing server-side, so poll-pause-on-hidden is politeness to the sync loop, not to the network.

**The auto-sync loop (the actual work).** In `workflowApiPlugin.configureServer` (`workflow-api.mjs:651-670`), add a timer that, while a browser has been seen recently (presence-gate: any `GET /api/workflow` within the last ~5 min), every 60–120 s runs a _change probe_ and, on change, `applySyncTrigger` (`:463-494`) — reusing the existing `pnpm sync` path, warnings channel and all. Cheapest probe: one conditional GitHub request, `GET /repos/{repo}/issues?state=all&sort=updated&direction=desc&per_page=1` with `If-None-Match` — 304 is free and means "no issue changed" (GitHub docs: "Making a conditional request does not count against your primary rate limit if a `304` response is returned"; fetched live 2026-09-10). Add an in-flight mutex (sync is already long: dozens of tracker reads + `vp fmt --write`, `package.json:28`). **Risks to verify in `pnpm dev` (not run for this note):** (1) rewriting `src/data.generated.ts` is watched by Vite; since `src/data.ts:1-5` re-exports it through non-component modules, a sync may already trigger a full page reload today (the manual Run sync button exercises this path) — if so, add `server.watch.ignored` for that file so auto-sync doesn't reload the page every tick, and let the polling atom be the only refresh path; (2) sync cadence × tracker calls vs the 5,000/h budget (§4's arithmetic); (3) each sync prints a console block and reports telemetry once per day (`scripts/telemetry.mjs:10`) — acceptable, but visible.

**Staleness affordance.** Add `meta.syncedAt` (ISO string): the server already stats the file (`workflow-api.mjs:54`), and sync can stamp it at generation (`sync-data.mjs:276-288`) — both payload copies (`WorkflowStateMeta`, `src/types.ts:141-144` / `src/schema.ts:162-165`; plumb through `workflowStateFrom`, `src/lib/workflow-state.ts:7-14`). Needed because today's header stamp is **not** freshness: `meta.snapshot` is the host repo's HEAD _commit_ time (`sync-data.mjs:173-178`) rendered as "LOCAL SNAPSHOT …" (`site-header.tsx:34-37,51-53`). Then a "synced 42s ago" chip in `site-header.tsx` (amber past a threshold; "static" text when `useWorkflowMode()` is static) — and move or duplicate the manual Run sync button (`OverviewPage.tsx:284-331`, wired at `src/routes/index.tsx:42-67`) next to the chip so any page can force a refresh; manual sync remains the escape hatch, auto-sync just removes the need to reach for it.

## 4. Time-in-phase

**Verdict: feasible with one new collector call family and an additive schema field. ~1.5–2.5 dev-days.**

**What GitHub gives (verified live 2026-09-10).** `GET /repos/{owner}/{repo}/issues/{issue_number}/events` "lists all events for an issue"; `labeled`/`unlabeled` events carry `label.name`, `label.color`, `created_at`, and `actor`; pagination `per_page` max 100 (default 30), statuses 200/410 (GitHub REST docs, fetched live). Probe on issue #7 returned real transitions:

```json
{"event":"labeled","label":"ready-for-agent","at":"2026-09-03T21:03:56Z"}
{"event":"labeled","label":"workflow:specced","at":"2026-09-04T18:41:35Z"}
```

The richer timeline endpoint (`…/issues/{n}/timeline`) adds comments, cross-references, commits, reviews — unnecessary bulk for this feature; the events endpoint is the right source. Authenticated rate limit confirmed live at 5,000/h (`gh api rate_limit` → `core.limit: 5000`; `X-Ratelimit-Limit: 5000` header on an events call).

**The semantic rule (the probe earned its keep).** Issue #79's events:

```json
15:11:55 labeled workflow:ticketed      15:32:12 labeled workflow:implementing
19:11:40 unlabeled workflow:ticketed    19:11:40 unlabeled workflow:implementing
19:11:40 labeled   workflow:shipped
```

Between 15:32 and 19:11 the issue wore two `workflow:` labels — the skills add the next label without removing the previous, so the double-label window is _normal operation_, not an accident. Therefore: **`phaseSince` = the `created_at` of the most recent `labeled` event whose `label.name` is the resolved phase's vocabulary label.** Re-entry resets the clock, which matches the flow (prototyping hands back to grilling, `docs/agents/workflow-labels.md:12`). It must be **null** for: pre-flow items; decision tickets (derived phase, no label — `display-state.ts:77`; render "decided/kind-based" instead of a duration); and reads that failed or hit the cap (warn, never fail the sync — the two-workflow-labels posture).

**Where it lands.** Collector: a `fetchIssueEvents` paged walk beside `fetchIssueComments` (`scripts/tracker/issues.mjs:139-180`), a pure `phaseSinceFromEvents(events, phase, vocabulary)` beside `phaseFromLabels` (`scripts/tracker/labels.mjs:96-116`), and a post-pass in `collectTrackerState` (`scripts/tracker/index.mjs`) that fetches events only for records with `phase !== null` that are not decision tickets — under its own `MAX_EVENT_READS` budget modeled on `MAX_ISSUE_READS = 250` (`index.mjs:34`), degrading with a warning. **The seam's write path needs the same discipline**: `readIssueRecord` (`workflow-api.mjs:98-114`) upserts records after every action; a phase move should set `phaseSince` to the write time (the label write just happened), and non-phase actions must carry the previous `phaseSince` over from `state.workItems`, or every edit silently resets the clock.

**Field shape — recommend `phaseSince: string | null` (ISO), not a transitions array.** It matches the record family's nullable convention (`phase`, `category`, `decidedAt`), answers the card's one question ("4d in implementing"), and keeps the generated snapshot small; a `phaseHistory` array is a strictly additive v2 if burndown charts are ever wanted. The double-write: `WorkItemRecord` in `src/types.ts:102-114` **and** `WorkItemRecordSchema` in `src/schema.ts:96-108` (excess-property rejection makes partial changes fail loudly, `src/schema.ts:486-489,560-562`); `src/data.generated.ts` regenerates on the next `pnpm sync`; **13 test files** with `WorkItemRecord` literals gain one line each (`tsc --noEmit` in `pnpm check`, `package.json:35`, enforces completeness).

**Call budget.** One events call per phase-labelled work item per sync (an issue exceeds 100 events only after real history — accept a second page). Today's sync for this repo is already ~10–30 calls (open page, map page, PR page, map sub-issues, per-closed-member comments and targeted reads, blocked-by lists — `scripts/tracker/index.mjs:87-257`). At N phase-labelled issues: N=60 → 60 calls/sync (≈80 syncs/h before touching the 5,000 budget); N=300 → 300/sync (≈16/h) — fine for manual sync, marginal next to a 60 s auto-sync loop. **Caching recommendation:** gate on `updated_at` — the issue list payload the collector already holds carries `updated_at`; skip the events call whenever it is unchanged since the last collection, persisting `{issueNumber: {updatedAt, phaseSince}}` in a small gitignored JSON cache in the app directory. This needs zero calls for untouched issues and avoids touching `requestJson`, which currently throws on any non-2xx and discards headers (`scripts/services/shared.mjs:42-57`) — ETag/304 support would require a dedicated helper (GitHub docs confirm a 304 "does not count against your primary rate limit", so it is the belt-and-braces follow-up). A free zero-cost companion: copy `updated_at` onto the record as `updatedAt` — no extra call, and it gives every card a "last touched" fallback where `phaseSince` is null.

## 5. Build order

1. **PR 0 — payload additions (½ day):** `meta.syncedAt`, payload `warnings`, optional `updatedAt` on records; header "synced Ns ago" chip. Small, additive, and both later features consume it.
2. **PR 1 — flow board, read-only (1–1.5 days):** `/board` route + nav, `src/lib/board.ts` derivation, shipped-issue bounded query, chips (blocked/frontier/parked/caveats). Decision-ticket mapping gets settled here.
3. **PR 2 — phase moves through the seam (1 day):** `PhaseMove` schema pair, `applyPhaseMove`, wire-grammar action kind, board/panel affordances, static-mode commands.
4. **PR 3 — live board (1–1.5 days):** polling atom with visibility-pause; server auto-sync timer with change probe, mutex, presence gate; HMR/reload behaviour verified and `server.watch.ignored` added if needed.
5. **PR 4 — time-in-phase (1.5–2 days):** events collector + `updated_at` cache, `phaseSince` double-write, action read-back carry-over, card rendering ("4d in implementing", shipped "2d ago").

Each lands as one coherent reviewable change (the repo's push discipline), and each is independently shippable: the board is useful before it is live, and live before it measures time.

## Open questions

1. **Decision-ticket→phase mapping** (§2): the proposed kind/state table is invented, not sourced — it needs an explicit decision (a small `wayfinder:` doc edit would make it parseable truth like the phase table).
2. Should `workflow:*` hand-moves from the board warn when they contradict triage state (e.g. moving `implementing` while `needs-info` — the caveat at `display-state.ts:48-52` covers display, not the write)?
3. Auto-sync default interval and whether it should be config (`workbench.config.json`) or env — and whether sync's console output should quiet down when machine-triggered.
4. Does a shipped column that only holds the newest ~100 closed `workflow:shipped` issues suffice, or does the team want full history (a bigger bounded-label-query decision, ADR 0009:27)?
5. Confirm in `pnpm dev`: does a sync-triggered rewrite of `src/data.generated.ts` currently full-reload the page (§3 risk 1)?
