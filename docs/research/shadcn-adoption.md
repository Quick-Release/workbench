# Adopting shadcn/ui in @quick-release/workbench

**Date:** 2026-09-03
**Sources:** primary only — ui.shadcn.com docs and the live component registry (`ui.shadcn.com/r`), tailwindcss.com docs, the `shadcn-ui/ui` and `TanStack/table` GitHub repos, viteplus.dev, and the npm registry (all queried live on this date). Repo files read: `package.json`, `vite.config.ts`, `tsconfig.json`, `index.html`, `bin.mjs`, `src/styles.css`, `src/main.tsx`, `src/types.ts`, `src/schema.ts`, `src/routes/index.tsx`, `src/components/*.tsx`, `src/lib/table.ts`.

## TL;DR

**Verdict:** yes — shadcn/ui can be added to this project, and every existing component can be rebuilt on shadcn primitives with no framework conflict. The historical blocker we feared most does not exist: shadcn's current Data Table docs **already target TanStack Table v9** (`useTable`, `tableFeatures`, `createSortedRowModel`, `columnHelper.columns`) — the exact API this repo already uses in `src/lib/table.ts:17-21` and `src/components/TicketTable.tsx:55-60`. The table migration is therefore markup-only (swap `<table className="signal-table">` for the shadcn `<Table />` shell); all sorting/filter logic stays untouched.

Three real caveats:

1. **vite-plus compatibility is the one unverified surface.** `vp` wraps Vite ("standard Vite config", "integrates with the existing Vite ecosystem" per viteplus.dev), but no doc shows `@tailwindcss/vite` under it. A 30-minute local smoke test (`pnpm dev` / `pnpm build` / `pnpm test`) must gate the migration. See §3 and §10.
2. **shadcn is vendored source, not a dependency.** Components land in `src/components/ui/` and you own them. Because this package ships `src` to consumers and runs `vp dev` **on the consumer's machine** (`bin.mjs:31`, `files` in `package.json:7-15`), every new runtime dep (Tailwind, plugin, primitives library, `clsx`, `tailwind-merge`, cva, `lucide-react`) must go into `dependencies`, not devDependencies — same as `react`/`vite` already are. There is no built CSS in the tarball; CSS is compiled at consumer runtime by Vite.
3. **The dashboard's identity is config-driven.** `src/main.tsx:10-12` injects user-configurable theme tokens (`workbench.config.json` → `WorkbenchTheme`, `src/types.ts:86-104`) as CSS custom properties at runtime. The migration must keep that working by defining shadcn tokens in terms of the existing variables (`--background: var(--bg)`) rather than accepting shadcn's stock neutral theme and squandering the acid-green look.

**Recommended first step:** smoke-test Tailwind v4 under vite-plus on a branch (add `tailwindcss` + `@tailwindcss/vite@^4.3`, wire the plugin into `vite.config.ts:15`, replace `src/styles.css` imports last), then run `pnpm dlx shadcn@latest init` and map tokens per §7. Migrate leaf components first (`StatusBadge`), tables last.

## 1. What shadcn/ui is (and is not)

shadcn/ui is **not an npm dependency you import components from**. The CLI copies component source into your repo (`src/components/ui/` by default) and installs the underlying runtime libraries. Verified against the live registry: fetching `https://ui.shadcn.com/r/styles/new-york-v4/badge.json` (what `shadcn add badge` consumes) returns a single registry item whose `files` are the full `badge.tsx` source and whose `dependencies` are `["radix-ui"]` — the CLI writes the file and installs the dep. The `utils` item ships `lib/utils.ts` containing the `cn()` helper (`twMerge(clsx(inputs))`) with deps `["clsx", "tailwind-merge"]`; the `index` style item depends on `class-variance-authority`, `lucide-react`, and `radix-ui` (all fetched live, 2026-09-03).

Consequences: vendored files are yours to edit (variants, tone mappings, markup); upgrades are a git diff you choose to take (§8); and the "components" ship inside this repo's published tarball because `files` already includes `src` (`package.json:7-15`).

Configuration lives in `components.json` created by `shadcn init`: `style` (use `"new-york"`; the old default is deprecated), `tailwind.config` (**leave blank for Tailwind v4**), `tailwind.css` path, `tailwind.baseColor` (`neutral | stone | zinc | mauve | olive | mist | taupe`), `tailwind.cssVariables`, `rsc` (false here), `tsx` (true), and five `aliases` (`components`, `ui`, `lib`, `hooks`, `utils`) backed by `compilerOptions.paths` or `package.json#imports` ([components-json docs](https://ui.shadcn.com/docs/components-json)).

## 3. Installation & setup for this stack (Vite + Tailwind v4, no Tailwind today)

The official existing-Vite-project path ([installation/vite](https://ui.shadcn.com/docs/installation/vite)):

1. `pnpm add tailwindcss @tailwindcss/vite`; replace the CSS entry's contents with `@import "tailwindcss";` (here: `src/styles.css`, imported at `src/main.tsx:9`).
2. `tsconfig.json`: add `"baseUrl": "."` + `"paths": { "@/*": ["./src/*"] }` to `compilerOptions`. The guide also edits `tsconfig.app.json`, but this repo has a **single** `tsconfig.json` (`tsconfig.json:1-21` has no `paths` today), so one edit suffices.
3. `vite.config.ts`: `pnpm add -D @types/node`, register the plugin and alias — `plugins: [react(), tailwindcss()]` and `"@": path.resolve(__dirname, "./src")`.
4. `pnpm dlx shadcn@latest init` (creates `components.json`, writes theme CSS + `lib/utils.ts`), then `pnpm dlx shadcn@latest add badge card table …`.

**vite-plus specifics.** This repo's config imports `defineConfig` from `vite-plus` and the `vite` package is aliased to `@voidzero-dev/vite-plus-core` (`package.json:43`; `vite.config.ts:1`). vite-plus documents "Use standard Vite config in `vite.config.ts`" and claims it "integrates with the existing Vite ecosystem" ([viteplus.dev](https://viteplus.dev)) — the site names no Tailwind guidance, no plugin-ordering rule, and no Vite version mapping for 0.2.x, and its own migration prerequisite says "Upgrade to Vite 8+" ([llms-full.txt](https://viteplus.dev/llms-full.txt)). Reassuringly, vite-plus's own ecosystem already contains `@vitejs/plugin-react` (this repo, `package.json:38`) — a standard Vite plugin — working in the same `plugins` array the Tailwind plugin would join (`vite.config.ts:15`). **Unverified:** whether `@tailwindcss/vite` behaves identically under the vp dev/build pipeline (Rolldown-based) as under stock Vite, and whether it must sit before or after `react()` — stock-Vite docs don't prescribe ordering either ([tailwindcss.com/docs/installation/using-vite](https://tailwindcss.com/docs/installation/using-vite) shows the plugin with no ordering note). Verification is one smoke test: add the plugin, run `pnpm dev`, `pnpm build`, `pnpm preview`, `pnpm test` (`package.json:21-30`) and eyeball compiled utility output. `vp test` only exercises `src/**/*.test.{ts,tsx}` (`vite.config.ts:12-14`); the existing tests (`src/data.test.ts`, `src/lib/overview.test.ts`) are data-level, so no jsdom setup is implied.

## 4. React 19 + Tailwind v4 support status

**React 19: fully supported, long resolved.** The [React 19 doc](https://ui.shadcn.com/docs/react-19) describes the 2024-era npm `ERESOLVE` problem (Radix fix tracked in radix-ui/primitives#2952) and now flags itself as historical: "We have added full support for React 19 and Tailwind v4 in the latest release," with a status table marking radix-ui, cmdk, vaul, recharts and others as working under npm/pnpm/bun. The peer range became `"react": "^16.8 || ^17.0 || ^18.0 || ^19.0"`. The `--force`/`--legacy-peer-deps` flags it documents are **npm-only workarounds; "No flags are needed for pnpm"** — this repo is pnpm 11 (`package.json:53`). The [February 2025 changelog](https://ui.shadcn.com/docs/changelog/2025-02-tailwind-v4) records the component rewrites: "We've removed the forwardRefs and adjusted the types", "Every primitive now has a data-slot attribute", and "HSL colors are now converted to OKLCH".

**Tailwind v4: CSS-first, the default.** No `tailwind.config.js` — `components.json`'s `tailwind.config` field is "leave blank for Tailwind CSS v4" ([components-json](https://ui.shadcn.com/docs/components-json)); theme variables live in the CSS entry; `@theme inline` maps them to utilities (`--color-background: var(--background)` → `bg-background`), and dark mode is a `@custom-variant dark (&:is(.dark *));` line plus token overrides in a `.dark` selector ([theming docs](https://ui.shadcn.com/docs/theming)). shadcn's own Vite template pins `react ^19.2.6`, `tailwindcss ^4`, `@vitejs/plugin-react ^6`, `vite ^8`, `typescript ~6` ([templates/vite-app/package.json](https://github.com/shadcn-ui/ui/blob/main/templates/vite-app/package.json)) — every one of those majors matches this repo (`react 19.2.8`, `@vitejs/plugin-react 6.0.5`, `typescript 6.0.3`, vite-plus 0.2.8 tracking Vite 8). `@types/react 19.2.17` here is current; the docs carry no @types caveat.

## 5. Tables: the TanStack Table v9 question (resolved)

The [Table component](https://ui.shadcn.com/docs/components/table) is purely presentational (a styled `<table>` shell with `TableHeader/TableBody/TableRow/TableCell`); TanStack integration lives in the [Data Table guide](https://ui.shadcn.com/docs/components/data-table), which **states "This guide uses TanStack Table v9"** and installs `@tanstack/react-table` unversioned (= 9.2.4, this repo's exact version).

The v9 pattern the docs now teach is exactly what this repo already runs:

- `tableFeatures({ rowSortingFeature, sortedRowModel: createSortedRowModel(), … })` — cf. `src/lib/table.ts:17-21`;
- `useTable({ features, columns, data })` — cf. `src/components/TicketTable.tsx:55-60`;
- `createColumnHelper<Features, TData>().columns([...])` — cf. `TicketTable.tsx:7-42`;
- the docs note "there are no more get*RowModel table options" (v8's `getCoreRowModel()` is gone) and prefer `<table.FlexRender header={header} />` while confirming "the v8-style `flexRender(component, context)` still works too" — this repo uses the function form at `TicketTable.tsx:109,133` and `PlanTable.tsx:100,124`.

The official v8→v9 breaking-change map ([migrate-v8-to-v9 skill](https://github.com/TanStack/table/blob/main/packages/react-table/skills/migrate-v8-to-v9/SKILL.md), `library_version: 9.2.4`) confirms the deltas old shadcn/v8 examples would have hit: `useReactTable(options)` → `useTable({ ...options, features })`, every `get*RowModel()` option → a named `create*RowModel()` slot in `tableFeatures()`, `sortingFns` → the `sortFns` slot, and instance methods moved to prototypes (no destructuring/spreading of rows/cells — relevant because `TicketTable.tsx:131` calls `row.getAllCells()` through the instance, which is correct v9 usage). **Net: zero TanStack migration work is required to adopt shadcn tables; only the JSX shell and classes change.**

## 7. Theming migration (dark-only, config-driven)

**Token map.** shadcn tokens are plain CSS custom properties with semantic background/foreground pairs, authored as raw `oklch()` values, and mapped to utilities through `@theme inline` ([theming docs](https://ui.shadcn.com/docs/theming)). The existing `:root` tokens (`src/styles.css:1-25`) map almost 1:1:

| workbench (`src/styles.css`)                                                               | shadcn token                                                                         | note                                                                                                          |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| `--bg` `#101715`                                                                           | `--background`                                                                       | plus the body's radial gradients stay custom CSS (`src/styles.css:38-50`)                                     |
| `--ink` `#f1f3e9`                                                                          | `--foreground`                                                                       |                                                                                                               |
| `--panel` `#17211d`                                                                        | `--card`, `--popover`                                                                |                                                                                                               |
| `--panel-hi` `#1d2b25`                                                                     | `--accent`, `--secondary`                                                            | hover/elevated surfaces                                                                                       |
| `--muted` `#a5b0a4`                                                                        | `--muted-foreground`                                                                 |                                                                                                               |
| `--faint` `#718076`                                                                        | custom `--faint` (or `text-muted-foreground/60`)                                     | the docs' custom-token recipe: define in `:root`, expose in `@theme inline` as `--color-faint` → `text-faint` |
| `--line` `#2b3a32`                                                                         | `--border`                                                                           |                                                                                                               |
| `--line-strong` `#45574b`                                                                  | `--input`                                                                            |                                                                                                               |
| `--acid` `#c5e86c`                                                                         | `--primary` **and** `--ring`                                                         | acid is the brand/focus color today (`src/styles.css:11,91`)                                                  |
| `--acid-dim` / `--amber(-dim)` / `--coral(-dim)` / `--blue(-dim)` (`src/styles.css:12-19`) | custom tone tokens (`--tone-good/-warn/-hot/-info` pairs) consumed by Badge variants | `--warning` is literally the docs' custom-token example                                                       |
| (none)                                                                                     | `--destructive`, `--chart-1..5`, `--sidebar-*`, `--radius`                           | destructive has no current equivalent; sidebar set is unused                                                  |

Hex values need conversion to oklch (or keep hex — they're valid CSS variable values; oklch is the docs' convention, not a requirement). **Radius:** the design is deliberately sharp — `border-radius: 0` on inputs (`src/styles.css:559`) vs `999px` pills (`src/styles.css:789`). Set `--radius: 0rem` (default is `0.625rem`; the whole scale derives from it via `calc()` per the theming docs) and Badge keeps its own `rounded-full`.

**Dark-only.** shadcn's dark mode is "overriding the same tokens inside a `.dark` selector" ([theming docs](https://ui.shadcn.com/docs/theming)); the Vite dark-mode guide shows a `ThemeProvider` whose job is toggling that class ([dark-mode/vite](https://ui.shadcn.com/docs/dark-mode/vite)). No "dark-only mode" is documented as such — which is good news: a dark-only app just **hoists the dark values into `:root`** (this repo's values already sit in `:root` with `color-scheme: dark`, `src/styles.css:1-2`), keeps `@custom-variant dark` for any vendored `dark:` utility classes, skips both the light block and the ThemeProvider, and optionally hard-codes `class="dark"` on `<html>` (`index.html:2`). Keep `color-scheme: dark` so form controls stay dark.

**The config-driven wrinkle (unique to this repo).** `src/main.tsx:10-12` copies every `overviewData.meta.theme` entry onto `documentElement.style` as `--ink`, `--bg`, … — a user-facing theming feature fed from `workbench.config.json` through `WorkbenchThemeSchema` (`src/schema.ts:56-74`, `scripts/sync-data.mjs:505`). Because both layers are ordinary custom properties, the non-breaking migration is to define the shadcn layer in terms of the old names — `--background: var(--bg); --foreground: var(--ink); --primary: var(--acid);` — so existing configs keep overriding the look with zero schema change. Renaming config keys to shadcn token names is the cleaner long-term shape but is a **breaking change** to `workbench.config.json` consumers (`workbench.config.schema.json`, `src/types.ts:86-104`).

## 8. Publishing & maintenance consequences for THIS package

- **What ships:** `files` is `bin.mjs`, `scripts`, `src`, `index.html`, `vite.config.ts`, `tsconfig.json` (`package.json:7-15`) — there is **no `dist/` and no built CSS**. `bin.mjs` runs `sync-data.mjs`, a `vp fmt` pass, then `vp dev --port 4051` **on the consumer's machine** (`bin.mjs:21-31`). So the dashboard is compiled from source at consumption time; Tailwind + `@tailwindcss/vite` + the primitives library (`radix-ui` or `@base-ui/react`) + `clsx`/`tailwind-merge`/`class-variance-authority`/`lucide-react` must all be **`dependencies`** (the repo already puts `react`, `vite`, `typescript`, `vitest` there — this package's model is unusual but internally consistent, `package.json:34-47`). Any Tailwind classes must therefore survive the consumer-machine compile: source detection is automatic in v4 (no content globs to mis-configure — [tailwindcss.com](https://tailwindcss.com/docs/installation/using-vite)).
- **What does NOT ship:** the shadcn CLI itself and `components.json` are dev-time concerns; consumers never invoke `shadcn` — they receive already-vendored `src/components/ui/*` and compiled-on-the-fly CSS. Keep `components.json` in the repo for future `add` runs (add it to `files` only if you want power users to extend the dashboard).
- **Upgrades:** the CLI's current command set ([CLI docs](https://ui.shadcn.com/docs/cli)) has **no standalone `diff` or `update` command** (that premise is outdated). The supported loop is: `shadcn add badge -o` (`--overwrite`), `init --reinstall`, `add --diff <path>` / `--view <path>` to preview, plus `migrate` codemods (`cn`, `icons`, `base-color`, `rtl`, `radix`) and `eject`. Practically: vendored files are git-tracked source, so upstream changes are reviewed as normal diffs.
- **Bundle cost:** tarball grows by the vendored `ui/` sources (a few tens of KB of TSX); runtime cost is Tailwind's output (v4 generates only used utilities) + `lucide-react` icons actually imported. The heavy runtime deps are the primitives library and React itself — already this package's reality.

## 9. Recommendation

**Go — conditionally and incrementally.** The only genuinely unknown integration risk is Tailwind-under-vite-plus (§3/§10); everything else is verified compatible. Ordered plan:

1. **Spike (half day):** branch; `pnpm add tailwindcss @tailwindcss/vite`; wire the plugin (`vite.config.ts:15`); `@import "tailwindcss";` at the top of `src/styles.css`; keep all existing CSS below it. Run `pnpm dev`, `pnpm build`, `pnpm test`, `pnpm check`. If the pipeline breaks here, stop — that's the no-go gate.
2. **Init + theme (half day):** `pnpm dlx shadcn@latest init` (`-b radix` if you want the conservative base; otherwise default); add tsconfig `paths`; map tokens per §7, dark values hoisted into `:root`, `--radius: 0rem`; move the old token block into a compat layer so `main.tsx` injection keeps working.
3. **Leaf components (1 day):** `add badge card button input select progress`; rebuild `StatusBadge` (tone variants), `MetricCard`, the filter panel, and `SpecPanel`'s cards.
4. **Tables last (0.5–1 day):** wrap both tables in the shadcn `Table` shell; port sticky-header/`aria-sort` details; no logic changes (§5).
5. **Layout polish (0.5 day):** callouts, section nav, footer as composed custom markup on top of tokens; delete dead CSS from `src/styles.css` incrementally.

**Total: ~2.5–3.5 dev-days** including the spike, for a codebase of ~800 lines of CSS and 6 components.

**Risks:** (a) vite-plus/Rolldown plugin incompatibility (mitigated: spike first, and the escape hatch is `@tailwindcss/postcss`, which needs no Vite plugin slot); (b) design drift if defaults are accepted instead of the §7 token map; (c) vendored-source upgrade burden lands on this repo, not npm; (d) runtime deps multiply what consumers install (the primitives library is the big one — Radix unified is ~1.6.x and stable, Base UI 1.7.0); (e) dark-only + config-driven theming is a nonstandard shape — expect to hand-tune the init CSS.

**When the alternative is better:** if this dashboard is near feature-frozen, skip shadcn and adopt only its conventions — vendor `lib/utils.ts` (`cn()`) and use `cva` for `StatusBadge`/`MetricCard` variants, keeping the hand-written CSS. That buys the variant architecture for two tiny deps and zero pipeline risk, but forgoes the accessible primitives (dialogs, dropdowns, command palettes) and the dashboard-block ecosystem if the workbench grows interactive editing (it is currently read-only by design, `OverviewPage.tsx:163-165`).
